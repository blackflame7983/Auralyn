# NRの時間合わせと切替（Issue #100）

## 変更する動作

従来は現在の原音と、フレーム集約・窓処理で遅れたNR処理音を混ぜていた。
強度は主にこの混合率であり、強モードでも発声保護が働くと原音が戻る。
新しい `core/noise_control.rs` は、NRへ渡した原音と混合条件を同じ時刻まで保持する。
同梱nnnoiselessのモデル、窓、線形変換、弱/強/学習/会場の目標混合率は変更しない。

入力rateにおけるNRフレーム長をNとすると、収集待ちN−1と窓処理1フレームNから
信号対応の基準を `2N−1` samplesとする。48kHzでは959、44.1kHzでは881。
これはフレーム上の時間対応であり、フィルターの周波数別位相や非線形な声の変化、
機器・OBS・通話受信の遅延を表すものではない。#28の観測値やOBS同期値へ転用しない。
既存の遅延metadataのsignal delayは引き続きunknownとし、約10msのフレーム長と区別する。

Smart/会場の小振幅0.72倍処理は、NR入力と対応する原音の両方へ適用する。
発声判定・学習結果を含む混合条件も原音と同じ履歴に載せる。
混合率の変化は約5msで平滑化するが、発声保護が有効な区間では上限を即時優先する。
保護解除側はランプで戻す。モード/強度の変更だけではNRの履歴を初期化しない。

## ON/OFFと初期化

時間位置の異なる二経路を重ねるクロスフェードは行わない。

| 操作 | 動作 |
| --- | --- |
| ON状態で開始 | 原音/NR履歴の充足まで無音、その後約5msで復帰 |
| OFF→ON | 約5msで原音を減衰、無音で履歴を初期化、充足後約5msで復帰 |
| ON→OFF | 約5msでNR経路を減衰、無音で履歴を破棄、原音を約5msで復帰 |
| 減衰中の取消 | 現在の経路を保って音量を戻す。稼働中NRを無用にresetしない |
| muteの変更 | 履歴を破棄。実出力のmuteは従来どおり最優先 |
| Stop/機器・rate変更 | 既存のストリーム再構築でDSP状態を作り直す |

48kHzでOFF→ONの切替は約30ms（減衰5ms＋充足約20ms＋復帰5ms）。
無音をなくす保証はしない。OFF定常時は原音へ遅延を追加しない。
表の減衰・無音はNR段の動作であり、後段の内蔵残響/VSTのtailは強制消去しない。
緊急muteによる実出力の消音は別途、従来どおり優先する。
ON定常時は原音の早い到達も処理音へ揃うため、モニター/通話の体感遅延が変わり得る。
位相の打ち消しが減ることによる音量・ピークの変化も実機で確認する。

原音/混合条件の履歴は準備時に固定長で確保する。48kHzで959要素、対応上限384kHzで7679要素。
処理・切替・resetでalloc/free、待機、lock、I/Oを追加しない。
配信と自分用処理の分離構成、VSTバイパス、保存形式、IPCには変更を加えない。
自分用の分離モニターは従来どおりNR/VSTを通らない。

## 実機なしの検証

`src-tauri`で以下を使用する。デバイス/OBSを起動する統合テストは含めない。

```powershell
cargo test --locked --lib --bins --test audio_queue_contract --test msix_coexistence
cargo check --locked --all-targets
cargo clippy --locked --all-targets -- -D warnings
```

NR専用テストは `cargo test --locked --lib noise_control::tests`。
既知遅延のダミー処理で単一ピークと混合条件の対応を検証し、実NRで原音の遅延位置・
全処理音時の既存NR一致・モード変更時の履歴保持・左右/monoを確認する。
8/44.1/48/96/192/384kHz、端数callback、全モードと強度/発声保護、ON/OFF連打、
reset、NaN/Infinity、初回/切替中のalloc/free=0を対象とする。
単体試験で機器の対応rateや主観的な二重音解消を合格にしない。

## 2026-10-27のローカル確認

専用テスト12件、ライブラリ449件（既存の計測用1件はignore）、キュー2件、MSIX共存2件が成功。
全ターゲットのcargo check、Clippy（`-D warnings`）、変更Rustの整形確認、diffの空白検査も成功した。
`cargo build --locked --bin audio_engine --bin plugin_scanner`も成功し、専用worktreeのbinへdebug sidecarを配置した。起動はしていない。
別の最適化済みpanic=abortハーネスでも、切替・全モード・resetを含む48kHz/2状態/30秒の
処理区間でalloc/realloc・解放0を確認した。計測器の陽性対照は確保・解放を検出した。

#93で使った英語の無騒音/小声相当6素材を、実際の新しいコントローラーで再処理した。
原音40%/処理音60%のSTOI平均は旧混合0.806082、新混合0.996217。
新混合は959sampleの信号対応を補正して参照音声と比較した。元は22.05kHz OGGを48kHzへ変換した
代理素材であり、日本語・歌・実ゲーセン・本人の自然さ/二重音解消を検証した結果ではない。

別の非instrumented releaseハーネスで、48kHz/2状態/30秒・480sample単位を各3試行した。
CPUはprocess user+kernel時間/audio秒（100%を1コア分）。初期化/I/Oを除外する。
定常の処理時間は最初の100ブロックを除外。p95は各試行のp95の中央値、最大は3試行全体で除去なし。

| 指標 | 旧混合 | 新混合 |
| --- | ---: | ---: |
| 1コア換算CPU・中央値 | 0.781% | 0.833% |
| 定常p95 | 0.1194ms | 0.1137ms |
| 定常最大 | 2.379ms | 0.732ms |

Windows 11 Pro・Ryzen 7 7800X3D・Rust 1.92.0/MSVC、opt-level=3/LTO/panic=abort。
中央試行は実行順を逆転。背景負荷/affinityは未統制、CPU時刻の分解能による丸めもあるため、
性能向上や最悪時間を主張しない。初期化は旧/新の両方を用意するハーネスなので比較対象外。
メモリは準備時に確保する履歴容量と処理区間の割当ゼロを確認した範囲であり、
Engine全体のCPU/RSS/Private Bytesや長時間運転の証拠にはしない。

ローカルの `src-tauri/target/nr-alignment-offline/` に比較用ソース/lock、
非instrumented版と割当監査版を別々に保存し、`quality.json` / `performance.json` に結果を保持。
生音声・実行ファイルはGit管理/Issue添付へ含めない。配布sidecarの起動や実機ストリームの開始は行っていない。

## 実機で残る受入

- 保存設定を保護し、実行Host/Engineの識別、OS、機器/driver、rate/buffer/ch、NR値、経路を記録する。
- VST/内蔵残響/外部モニターなしの単一経路でNR OFF/ON、弱、強・内部強度1.0・発声保護OFF、発声保護ON、学習/会場を比較する。「原音比較」はVSTだけのバイパスである。
- 自宅の普通声/小声/語頭語尾/固有名詞/実況/叫び/笑い/歌を聴き、OBS録画と通話相手側を別々に確認する。自分用の歌唱モニターの遅延も確認する。
- ゲーセンの実騒音・近接/離れたマイク・持込/共有相当の条件で確認する。別経路のゲーム音を保持する。
- 機器直接モニター、OBSモニター、Windowsの「このデバイスを聴く」、重複source、通話側NR/AGCを一つずつ戻し、経路の二重化を切り分ける。
- WASAPI/ASIO、実対応44.1/48kHz、異なるbuffer、機器切替、切替連打、mute/Stop/再開、ゲーム/OBS並行負荷と連続運転でクリック・音切れ・CPU/メモリ・ピークを確認する。

実機未実施の間は #100 をOPENのまま維持する。#93のDeepFilterNet標準モデルは追加候補として残し、改善後の固定ソースを基準として再比較する。
