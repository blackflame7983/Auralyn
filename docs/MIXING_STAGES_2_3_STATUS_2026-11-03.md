# 二入力とミックス後VSTの実装・確認記録

2026年11月3日時点の作業記録。公開済みの機能を示す文書ではない。

## 段階2の実装

声用途の主入力へ、音楽用途のプロセス入力またはWASAPI機器入力を追加した。
本人用の出力callbackで一度取得して分岐し、配信枝だけで既知の声処理待ち時間と手動オフセットを合わせる。
正の値はオケ側、負の値は声側を追加で待たせる。上限は±2,000 ms。
申告されないVST遅延をゼロと仮定せず、耳やOBSまでの総遅延とは区別する。

独立した入出力クロックは、取得rateとキュー量に基づく可変比変換で扱う。
同じASIO機器の入出力だけは共有クロックとして扱い、ASIO主入力とWASAPIオケの混在は独立したオケのクロックを補正する設計とした。
この環境でASIOの実入力は確認していない。
仮想ケーブル経路も実Engineで取得を確認した。

音量は0〜2倍、トラック別ミュート、本人用のオケ返し、配信側の時間差を操作できる。
オケ終了時はオケを無音にし、声の処理を継続する。
設定変更には世代とrevisionを要求し、保存したPIDやアプリ名だけでは再接続しない。
再起動後は入力元を明示選択する。
壊れた保存設定は明示的な初期化で原本と状態記録を保管し、オケを無効にできる。

## 段階3の実装と全体復帰

ミックス後VSTは専用のEngineプロセスへ分離する。
既存の声ラックとインスタンス・順序・状態・エディタ・保存領域を共有しない。
音声は固定容量の共有メモリキューで渡し、本人用callbackで配信VSTを待たない。
OSのマッピングと後始末は制御側で行い、音声callbackでは確保・解放・ロック・I/Oを行わない。
Windowsの共有メモリと生存期間は[Microsoftの公式説明](https://learn.microsoft.com/en-us/windows/win32/memory/sharing-files-and-memory)に従う。

処理順は「声処理・時間合わせ・ミックス・ミックス後VST・最終音量・ピーク保護・配信出力」。
ミックス後ラックの失敗や応答欠落は配信枝を無音停止し、無断で加工前の音へ切り替えない。
旧プリセットの役割は声ラックのままとした。
新しい全体保存はschema 5で、声ラック、オケ設定、ミックス後ラック、出力と本番モードを含める。
過去の保存形式を現在のミックスへ適用して、追加の設定を黙って省略する操作は拒否する。
一時利用の原本にはorigin 3を追加し、機器IDと両ラックの状態を含むチェックサムを検証する。
原本形式の単体試験に加え、一時利用からのschema 5手動復旧も実Tauriで確認した。詳細は次節に記録する。

### 全体復帰が止まる原因と修正

最初の実Tauri確認では、保存の適用が`complete=false`となり、出力音量の反映待ちが失敗した。
診断ログでは、`restore_plugin`の後にTDR Novaから`flags=28`の通知が届いていた。
これはパラメーター値・遅延・パラメーター名の更新を合わせた通知で、声ラックはこの時点ですでに動作中だった。
追加した再設定検出が配信枝を停止し、後続の音量変更を処理できなくなっていた。

復帰の順序を「主音声を停止し、声とミックス後の両ラックを復元 → 準備済みの声ラックを保持 → 主音声を一度だけ開始」へ変更した。
開始後の共通処理では声VSTと入出力構成を重ねて適用しない。
開始結果の機器ID・rate・buffer・ルーティングが一致しない場合は失敗とし、無断の再開始を行わない。
通常運転中に届く再設定要求では、配信枝を無音停止する保護を維持している。

修正後の`postmix-host-native-7`で、次を実Tauriと実Engineで確認した。

- 画面からschema 5を保存し、声用とミックス後のラックを独立して操作できる。
- 全体復帰とUndoが完了し、両ラックのstateハッシュとミックス設定が一致する。
- 全体ミュートを維持し、VST不在では適用しない。
- 再起動後は、保存したミックス後ラックの明示復元とオケの再選択を要求する。
- 破損した保存設定の原本を保管して復旧でき、全出力先の状態と所有プロセスを回収できる。

1〜6回目の失敗記録も同じ証跡領域に保持した。
1〜2回目はUI検証スクリプトの要素指定・非同期反映待ち、3〜6回目は全体復帰の未完了を記録している。
実VSTの通知を記録した5〜6回目と、修正後に同じ通知による停止が生じない7回目を区別する。

部分失敗時は送出を停止し、別保存の全体原本から手動復旧する既存契約を維持する。
設定ファイル全体を一つの取引で置換する実装ではないため、入出力・本番モードの現在ファイルには部分反映が残り得る。
オケとミックス後ラックの設定は、自分が書いた内容を排他ハンドルで照合して戻す。外部編集を上書きしない。
復旧原本が残る場合は自動開始を抑止する。

### 一時利用から両ラックを手動復旧

`73021db`の専用アプリで、一時利用へ切り替える際にschema 5・origin 3の原本を退避し、通常設定へ戻った後の手動復旧を確認した。
`postmix-checkpoint-native-1`では声・配信の両方にTDR Novaを使い、個別のgainとミックス値を照合した。
この組合せでは両VSTのstateが同一だったため、追加の`postmix-checkpoint-native-2`では声にTDR Nova、配信にOTTを使った。
異なるstateのSHA-256、各プラグインのpath、声gain 0.42・配信gain 0.37、時間差73 msが復旧後も一致した。

両試験とも全体ミュートを維持し、通常設定へ戻った後に保存ラックの明示復元とオケの再選択を要求した。
手動復旧は完了し、元の退避ファイルのバイト列を保持し、一時領域を削除できた。
試験用Host・Engine・音源を回収し、全再生・録音端点のミュート・音量・既定設定が元の状態と一致した。
Host・Engine・scannerの実ファイルSHA-256はビルド情報と照合した。
これらは隔離設定と仮想入力による確認で、物理マイク・ASIO・聴感・OBSの受入とは分ける。

### 出力callbackと入力不足の計測を訂正

`73021db`で、分離時の配信workerの実行間隔をOSの出力callbackの遅れとして数えていた箇所を修正した。
本人用callbackとworkerの処理単位が異なると、workerには正常でも長い待ちが周期的に生じる。
現在の`glitch_count`と`max_jitter_us`は、OSが呼ぶ出力callbackの入口で、直前の実フレーム数に対応する再生時間からの遅れを測る。
前者は再生時間の半分を超えて遅れた回数で、可聴の音切れの回数ではない。
`callback_diagnostics`の処理時間とブロック数は、分離時には引き続き`broadcastWorker`の値となる。
二つの観測対象を混ぜて割合や期限超過を算出しない。

主入力キューの出力側統計は本人用callbackだけで更新する。
SRCの入力先読み量や、producerが並行して追加するキュー残量の差から、出力不足を推定しない。
実際に生成した出力フレーム数を使い、意図的な復旧バリアの停止を不足から除外する。
SRCの故障でcallback全体を無音にした場合は、その一回分を不足として記録する。
プロセス単独入力のSRCも同じ生成フレーム数の基準に揃えた。

回帰試験では44.1・48・96 kHzの入力から48 kHzへの変換、入力枯渇時の全体無音、意図的な停止、実ブロック長による間隔判定を確認した。
Rustの全対象試験はlibrary 685件成功・環境依存5件保留を含めて成功し、厳格なClippyも成功した。

### 実信号による短時間の比較計測

`2ffa7d4`の固定Engineを使い、48 kHz・要求512 frames・声側TDR Nova・NR OFFを共通条件として、配信VSTなし→あり→あり→なしの順で各60秒運転した。
配信側もTDR Novaを使い、同じ音源WAVとVSTのSHA-256を記録した。
主入力は仮想ケーブルの合成音、オケは所有Chromeの音源、本人用はWindows既定のVoicemeeter Input、配信先は未使用のRealtek Digital Outputとした。
証跡は`short-active-2/`の各`summary.json`・`samples.jsonl`と、集計した`summary.json`。
EngineのSHA-256は`4107901b9ed6a75440230f792cb7aef8439df9522f7d5ace6f1710f28d313c19`。

全体ミュートでは配信VSTへの転送も止まるため、計測中は解除し、VST後のmaster gain、両出力trimを0にした。
本人用ミュートと、原音・配信先の端点ミュートも併用した。
毎回のメーター通知が存在し、出力peakが0であること、両入力とmixが非ゼロで加工が有効なことを継続確認した。
配信VSTでは、有効ラックの確認に加え、処理して出力キューへ公開したパケット数の増加も確認した。
この数値は既存の共有キューの公開位置から制御側で読み、音声側に新たなロックや確保を追加しない。

CPUは60秒全体の主Engineと配信用Engineの合計。カウンターは最初の観測から最後までの58秒の差、最大追加遅れは音声開始以降の値である。
全試験の観測窓内で、zero-fill・underflow、主入力SRCのunderrun、オケの不連続・時刻異常・非有限値・待機破棄・再待機は増加0だった。
配信VSTの転送待ちは2,048 frames、申告遅延は184 framesを維持した。
声側workerの最長処理時間は0.968〜1.332 msで、512 frames分の10.667 msを下回った。
全再生・録音端点の設定復帰と、所有プロセスの回収も成功した。

今回の値はdebug buildで、Engine起動時の性能調整は`AURALYN_DISABLE_PERF_TWEAKS=1`で無効にしている。
ビルドと他の検証を並行せず、試験音源・経路・設定を固定したが、別作業の音声Engineも動いており、Windows全体のCPU負荷は15.04〜28.13%だった。
CPUの差を、配信VST単独の厳密な追加負荷とは断定しない。
出力callback一回あたりの平均要求も520.28〜548.58 framesと変動した。間隔の遅延回数を欠損フレーム数や可聴音切れの回数へ換算しない。

この短時間の範囲では、VSTの停止や入力不足を伴う処理能力不足を検出していないため、バッファ量やDSP方式の変更は加えない。
callback間隔の変動と可聴音切れの関係は、実際の本人用の返し・OBS最終録音で確認する。
集計は`scripts/summarize_mixing_measurements.py`で再現でき、既存の原本や集計を上書きしない。

初回の`short-fixed-1`は全体ミュートによる配信VSTの待機時負荷として保管し、上表には使わない。
`short-active-1`の配信VSTあり試行は、runnerが専用Engineに許可されていない診断要求を送って停止した記録として保持した。
要求を稼働中も読めるラック情報へ直し、`short-active-2`を新しい領域で取り直した。

## 最終の自動確認と残る受入

段階3の実装時にはRust library 682件成功・環境依存5件保留を含む全対象試験、厳格なClippy、フロント1,511件、TypeScriptが成功した。
後続の計測修正ではRust library 685件成功・環境依存5件保留を含む全対象試験と厳格なClippyを再確認し、専用アプリのビルドでもTypeScriptが成功した。
処理進行カウンターの追加後も、同じ全対象試験と厳格なClippyが成功した。
900×600のブラウザモックではキーボードからの明示読込・0 gain・破損設定復旧を確認した。
これらは実Tauriでの保存・全体復帰・Undoの確認と分けて記録している。

物理マイク、ASIOとの混在、OBS最終録音、本人による聴感、48〜72時間の受入は残る。
長時間の連続運転は利用者の指示により実施時期を調整し、今回の後続確認では開始していない。
プロセス単独入力のASIO出力は未対応のまま維持し、未検証の組合せを利用可能とは表示しない。
試す手順は[二入力と配信VSTの確認手順](MIXING_AUDITION_GUIDE.md)を参照する。
