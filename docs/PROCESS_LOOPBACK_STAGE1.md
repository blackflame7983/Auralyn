# プロセス単独入力：段階1のローカル実装と検証記録

確認日: 2026-11-02。追跡: [Issue #233](https://github.com/blackflame7983/Auralyn/issues/233)。
設計・受入条件は[実装計画](plans/PROCESS_LOOPBACK_AND_MIXING.md)、着手判断の根拠は[段階0の追加検証](PROCESS_LOOPBACK_STAGE0.md)を参照する。
段階1までの実装・検証は`74a3aba`でコミット済み。段階1の受入全体や公開を完了したという記録ではない。
利用者による入力・比較切替の確認後、[切替ノイズを抑える後続変更](COMPARISON_SWITCH_TRANSITION.md)を実装。改善版の再試聴で、クリックノイズと音量低下は許容範囲と確認した。

## 実装した範囲

入力callbackを開始処理から分離し、従来の機器入力とプロセス取得を同じ出力処理へ接続した。
プロセス入力は、既存の`windows`／`windows-core` 0.62.2を使う専用MTAスレッドで取得する。新たな仮想ドライバーや`wasapi`の依存追加は行っていない。
取得は48 kHz・stereo・f32、本人用の処理と出力はWASAPI stereoを初期対応とする。

- 候補は全ての有効な再生エンドポイントの音声セッションから取得し、同じ実行ファイルの親をたどってプロセスツリーへ対応づける。Chromeのタブ単位では選ばない。Auralyn・engine・scannerとその子孫は除外する。
- Hostが候補IDからPIDと生成時刻を解決し、Engineの開始前にも再検証する。フルパスはUIへ渡さない。音を再生してから候補を更新・選択する。
- 原音の経路は、選択した別再生先だけであり、出力デバイス側がミュート済みであることを開始時に確認する。原音用と本人用の出力先が同じ場合は拒否する。対象終了、再生先移動、デバイスのミュート解除などを検出した場合は停止する。
- Auralynから元アプリの出力先・セッション音量・Windows既定を自動変更しない。利用者がWindows側で原音の経路を設定する。別再生先の機器やドライバーにより、取得音を保てない場合は仮想ケーブルを使う。
- 出力側で可変比SRCを動かす。キュー2,048フレームを目標に±2,000 ppmまで追従し、容量は16,384フレーム。通常の速度差を`queue_recovery`の反復破棄で隠さない。無音待ち、補正量、滞留、不連続、異常時の停止を観測する。
- 「声」はNR・ノイズ学習・既存の内蔵処理へ、「音楽」は声向けの処理を省略して既存VSTラックへ通す。既存のNR／内蔵処理の設定値は、用途の変更だけを理由にOFFへ書き換えない。音楽では声向けの測定・ボイスチェックを拒否する。
- ノイズ学習の識別は`process:<appKey>`とする。マイクとは共有せず、入力ごとに結果を退避する。入力変更による測定の失効と、別入力の学習結果を上書きすることは区別する。
- 設定画面には入力元、候補の更新・選択、原音の出力先、用途を追加した。入力元の切替で用途を変えず、アプリから機器への切替では機器を明示選択する。原音と加工後の出力、仮想ケーブルの再生側／録音側を案内する。通常のVSTバイパスがNRを含めた比較ではないことも示す。

プロセス取得は[Microsoftの公式サンプル](https://learn.microsoft.com/en-us/samples/microsoft/windows-classic-samples/applicationloopbackaudio-sample/)に従って子プロセス込みの取得を使う。
Windowsのビルド20348以降を開始条件とする。対象に再生ストリームがなくても、無音で取得自体は続き得る。無音を対象終了と同一視しない。

## 保存・再開と非対応の入口

保存するのは入力種別、用途、アプリの識別ハッシュ・名前、原音用の再生先である。
PID、生成時刻、候補IDは永続化しない。同じHost内で明示選択済みのアプリは停止後に再検証して再開できるが、Auralynの次回起動時にはアプリを選び直す。
古いPIDや同名の別プロセスへ自動接続しない。ホーム開始とVSTクラッシュ後の再開にも入力形式を渡す。

旧形式は従来の声の機器入力として読める。
未知・不正な新形式や、入力形式を扱えない復旧経路を、既定マイクへ読み替えない。
Engineの能力応答を確認してから新形式を送るため、旧Engineが未知の引数を無視してマイクを開く経路も拒否する。
プロセス単独入力ではマイクを開かず、マイク権限確認も開始条件にしない。

段階1では、アプリ入力・音楽の用途と、歌／雑談モード・本番保護・処理分離との組合せには対応しない。
接続設定を含むプロファイルや配信状態の保存・復元も拒否する。接続を含めないVST構成は使え、適用前の音作りのバックアップも接続設定を含めずに行う。
入力元・用途の切替は停止後に明示適用する。拒否する新入力の条件は、入力の学習状態などを変更する前に検証する。
ASIOマイク、通常の機器入力、既存のSRC・回復処理は維持し、マイク＋オケやミックス後ラックはまだ実装しない。

ブラウザ試験はIPCモックであり、実Tauriとは別の証拠である。実Tauriと実Engineではモックを使わない。試験用の実行ファイルは隔離先へコピーし、通常起動用の`src-tauri/bin`は差し替えていない。通常起動で試す場合は[ビルド手順](BUILD_GUIDE.md)に沿ってHostとsidecarを一緒に再ビルドする。
マイク権限を拒否したWindowsの状態、ASIOマイクの実機、第三者VSTを組み込んだ音質や安定性を、この表の成功に含めない。
旧形式と通常機器入力の回帰、ASIOの構築・再試行・チャンネル契約は自動試験で確認したが、今回ASIOマイクを使った実機録音はしていない。

## 受入として残る確認

- 通常のChromeプロファイル・各配信サイト・拡張機能、VLC以外のプレイヤーによる確認。後続の専用ChromeとVLCの試験を、すべてのアプリや素材の対応済みという意味にしない。
- 別再生先の切断・無効化、音声service以外の子プロセスの作り直し、元アプリが既定出力へ戻る場合。専用Chromeの音声service終了後の確認を、全種類の子プロセスへ一般化しない。
- 原音の二重再生、本人用の返し、VST加工後の音質を耳で確認すること。データ上のミュート・取得・出力の成功と聴感は分ける。
- 許諾済み素材の声用途でNRの有無は確認済み。強度と声の保持の比較、物理マイクの学習結果が変わらないことの確認は残る。WASAPI機器入力とプロセス入力の分離は制御音で確認済み。
- 65分試験で記録したcallback遅延の評価と聴感確認。Host画面を含む長時間運転、別のVST・再生条件でも確認する。段階0の30分の取得側試験とは別の証拠として扱う。
- マイク権限拒否下の実機確認、ASIOマイクの実機回帰、WindowsのDPI・読み上げ・各種再生機器での確認。

これらが残るため、段階1の受入完了とはしない。段階2〜3への着手や公開の判断も行っていない。
