# MSIXの設定分離・共存と移行計画

Issue [#4](https://github.com/blackflame7983/Auralyn/issues/4) の配布・設定保存を対象とする。
MSIXを今後の主軸とし、通常版EXE（NSIS）はMSIXの長時間試験と設定移行の確認が完了するまで維持する。
MSIは今後のビルド・配布・実機検証から外す。公開済みのMSIや過去のReleaseは削除しない。

## 今回の実装範囲

| データ | 通常版 | MSIX版 |
| --- | --- | --- |
| プリセット・フルプロファイル・VSTブラックリスト・ウィンドウ状態・前回の音声設定 | 従来のTauri app_config_dir（Roaming AppDataの既存identifier配下）を維持 | ApplicationData.Current.LocalFolder配下のAuralyn |
| localStorage・VSTセッション等のWebView2データ | 従来のapp_local_data_dirを維持 | ApplicationData.Current.LocalCacheFolder配下のAuralyn/WebView2 |
| app_cache_dir / app_log_dir | 従来どおり | 上記LocalCacheFolder配下のAuralyn/cache、Auralyn/logs |

WindowsのAPIが返すパッケージ専用フォルダーを使い、PFNやWindowsAppsのバージョン付きパスを固定値で組み立てない。
保存先はウィンドウ生成とプラグイン初期化より前に決める。MSIXで保存先を取得できない場合、通常版の設定やEXE隣へフォールバックせず起動を中止して案内する。
インストール形式を判定できない場合も、共有設定への書き込みを始めない。

MSIXから通常版の設定は自動取り込みしない。既存の試作版が通常版の領域へ保存した設定も同様。
MSIX専用領域に設定がなければ初回セットアップから開始し、通常版の音声やVSTを暗黙に開始しない。
OSの権限設定、外部VST本体、ドライバー、OBS自身の設定をコピー・変更する処理は追加しない。

## 共存

- 両版をインストールしたままにできるが、同一Windowsログインセッションで稼働させるホストは一つとする。
- Tauriのidentifierを維持し、保存先と二重起動防止の識別子を切り離す。single-instanceを最初のプラグインとして登録し、後発ホストはウィンドウ・音声ホスト・サイドカー・ホットキーの初期化へ進まない。
- 後発の起動では既存のウィンドウを表示・最小化解除・フォーカスし、同時実行できないことを案内する。版の切替はトレイの「終了」から行う。既存側を勝手に終了しない。
- 既存通常版の設定やインストール、試作版が残した旧データは削除しない。

自動起動のStartupTask対応は後続。現段階ではMSIX・判定不能から通常版のRunキーを参照・変更しない。
通常版も、登録内容が現在のEXEのコマンドと一致しない場合は上書き・削除を拒否して案内する。
Run登録の有無だけではWindows側の有効状態を保証しない。現在の表示にもその条件を明記する。

## 改修の順序

1. **今回: 保存先分離と共存**。通常版の保存互換性、MSIX専用領域、二重起動防止、自動起動登録を触らないガード、MSI除外を実装する。
2. **設定移行**。対応した通常版から明示的に書き出し、MSIXで内容確認後に取り込む。版番号付き形式、サイズ・形式検証、バックアップ、失敗時の復旧を用意する。WebView2の内部ファイルを丸ごとコピーしない。既存設定を無断で上書きしない。
   プリセット、VST状態、音声設定、ゲイン、内蔵FX、表示・音量目標・お気に入り・ブラックリストを対象候補とする。OBSパスワード・復元履歴、自動起動登録、録音途中のデータ、クラッシュ処理中の印は含めない。移行後の初回はデバイス・出力・VSTを確認するまで音声を開始しない。
3. **MSIX自動起動**。StartupTaskを初期OFFで宣言する。Windows側で無効にされた状態・ポリシー・API失敗を表示し、再有効化を強制しない。旧登録の整理は対象を確認して明示操作で行う。更新後・ログイン時の実起動も確認する。
4. **通常版の自動更新確認**。既存の手動更新に加えて起動後と長時間起動中の定期確認（目安1日）、継続表示する通知、任意の自動ダウンロードを追加する。確認失敗は通常動作を妨げず、手動確認を残す。適用は利用者の操作後に設定とVST状態を保存し、録音・試聴・音声処理・サイドカーを正常終了させてから実行する。稼働中の無断インストール・再起動はしない。Portable版の適用先も確認する。
5. **機能を揃えて回帰検証**。VST、音声、OBS、更新・削除・設定保持、マイク権限、900×600を確認する。設定移行と実MSIXでの共存を含む。
6. **数日間の個人試験**。同じrelease候補・実行パス・ハッシュを固定して目安48〜72時間運用する。普段の音声経路を中心に、CPU・メモリ・ログ容量・音切れ・デバイス復帰・OBS再接続・残存プロセスを記録する。ASIOの到着間隔カウンターと実際の音切れを区別する。自動適用で試験中の版を変えない。
7. **正式配布判断**。不具合修正後に必要な再確認を行い、正式Identityでの最終確認・Store申請へ進む。EXEの維持終了は長時間試験と設定移行の確認後に判断する。

Store版の更新はStoreに任せ、通常版のupdaterは登録しない。直接配布MSIXの自動更新方式は別途設計する。
今回の実装だけで2以降や正式Store配布の完了とはしない。

## 検証と境界

- Rust: 保存先解決、判定失敗時の拒否、Tauri path APIの解決結果、前回音声設定の独立保存、他方の自動起動登録を変更しない判定を確認する。
- Windowsの子プロセステスト: 保存先が異なる二つのTauri MockRuntimeに同じ識別子を与え、両方の起動順で後発のsetupへ到達しないことと、既存側への通知を確認する。実際のWindows mutex・メッセージ転送を使うが、インストールしたMSIXのトークンでの検証ではない。
- UI: MSIX等の変更不可・自動起動状態取得失敗・通常版の明示操作を確認する。IPCモックでありレジストリを変更しない。
- 配布: NSISのみの設定と、残存MSIを採用しないことを配布テストで確認する。

WindowsのMockRuntime統合テストにはCommon Controls v6のmanifestを埋め込む。build.rsの指定は統合テストだけに適用し、製品EXEのmanifestはTauriの生成を維持する。

#### 音声と表示で確認した制約

- マイク個別権限が`Prompt`の初回WASAPI開始は、エンジン応答のタイムアウトになった。状態取得もタイムアウトしたため、試験エンジンとホストを終了し、利用者による個別許可のON後に、選択し直した入出力で明示的に開始した。プロセス再起動なしでの復帰可否や、タイムアウトの原因は未切り分け。
- 許可後は合成音声をCABLE Inputへ流し、MSIXのWASAPI入力・SteamStreaming出力、48kHz/512 framesで音声処理を確認。更新前7.39秒・更新後6.93秒の加工前後WAVを取得した。48kHz・2ch・32bit floatで、ピーク約0.354、RMS約-23.8/-23.5dBFS。VST・内蔵処理なし、ゲイン1では各回の加工前後PCMが一致した。メーター通知は186/181回あり、更新後も`running=true`・`streamFailed=false`だった。
- WAVとメーターはアプリ内の入出力処理の証拠であり、物理マイクの発話、実スピーカーの聴感、出力端点のループバック録音を確認したものではない。MSIXのASIO経路も今回は再試験していない。
- 更新後の起動直後に「音量を確認できません。再操作してください。」が残り、900×600のフッターが916px幅となる場面があった。出力ゲインをキーボードで100→99→100%へ再操作すると警告が消え、音量1・確定済み状態とフッター900pxへ復帰した。今回の保存先変更に由来するかは未切り分けで、表示・起動時の確認課題として残す。

試験開始前の通常版2,627ファイルを退避し、終了後に全件のSHA-256一致まで確認して復元した。
サイズと更新時刻が変わらず内容だけ変わったWebView2キャッシュのindex 5件は、通常の同期コピーで省略されたため退避元から明示コピーし、最終照合では差分なし。

LocalMachineの公開証明書は利用者が管理者PowerShellで削除し、CurrentUser/LocalMachineのMy・Root・TrustedPeopleの6ストアで今回の証明書が0件であることを再確認した。
試験ホスト・エンジン・スキャナー、試験用WebView2、検証用ポート9230の待受も残っていない。
Windowsの全体／デスクトップアプリのマイク許可と、通常版の自動起動Run値は変更していない。

未確認は正式IdentityでのStore配布・更新、異なるアプリ版の設定移行、NSISのインストーラーによる更新・削除、別ユーザー／別ログインセッション、OSログイン起動、物理音声、48〜72時間の長時間運用。

### 同日の起動時不具合の修正

上記実機試験で見つかった未許可時のタイムアウトと、起動直後の音量警告を対象に追加修正した。

- MSIXのWASAPI開始前に、Windowsの`AppCapability("microphone").CheckAccess()`で実際の許可状態を確認する。初回の`UserPromptRequired`、利用者／システムによる拒否、確認不能では入力開始要求を送らない。明示的な開始・再試行・保存した設定での起動が同じガードを通る。OSの許可設定を変更・要求せず、既存のWindows設定案内へ戻す。通常版とASIOにはこのパッケージ専用判定を適用しない。
- 保存ゲインの起動時復元では、世代が変わっただけで失敗にせず、明示設定を上書きしない`initialize`を使って有限回の確認を行う。手動操作の反映確認は従来どおり世代変更を検出する。
- 復元失敗は定期的に再試行し、確認できたら起動時の警告を消す。手動設定の失敗とは状態を分け、背景の確認成功だけで手動失敗の案内を消さない。確認中の開始通知も保留して処理する。
- 音量警告は操作部の下段へ配置し、横幅を追加しない。操作部に高さを確保し、警告の色はライト／暗色それぞれで読める指定にした。

追加修正後の自動検証ではUI全250件、Rustライブラリ107件・キュー契約2件・共存統合2件、TypeScript型検査、`cargo check --locked --all-targets`、`cargo clippy --locked --all-targets`、release整合チェックが成功した。
UIテストは開始通知と初期確認の競合、一時失敗からの復帰、明示変更の保持、起動中の世代変更、ストリーム障害を含む。
途中の全体実行では未変更のModalLayerテスト1件が待機時間超過となった。対象3件と、その後の全250件は成功しており、最初の失敗の原因は特定していない。

実MSIXの初回`Prompt`では、UIの保存開始から約251msで権限案内へ戻った。追加の開始IPCは37ms、続く状態取得は2msで応答し、ストリームは停止したまま・サイドカー応答も正常だった。
「設定に戻って再試行」で入出力の選択を保持し、失敗した設定は保存されなかった。試験中の通常版2,627ファイルは全件ハッシュ一致。

最終版は`cargo build --bins --features tauri/custom-protocol --release`で本体・エンジン・スキャナーを同時にビルドした。
計測用featureやDEV/TEST用の設定は使わず、同じ試験用証明書でMSIXを更新した。インストール先の3 EXEは最終release出力とSHA-256が一致した。
