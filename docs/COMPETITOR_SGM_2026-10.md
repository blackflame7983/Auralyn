根拠は Stream Gear Mixer（以下 SGM）の[販売ページ](https://booth.pm/ja/items/8177399)と、説明書（2026-10-24 版、40ページ。版とハッシュは追加照合の記録を参照）。ページ番号は PDF 先頭を1とする。SGM は実機で動かしておらず、以下は資料に記載された仕様である。Auralyn 側は [UI/UX 監査](UI_UX_AUDIT_2026-10-27.md)の項目 ID で参照する。

## 1. 画面の作り

SGM の画面はミキサー卓の見た目で、文字が少なくても位置と色で意味が読める。Auralyn はカードと番号付き手順でできた「設定アプリ」の見た目で、説明文に頼っている（監査の総評、A2、C）。

| 観点 | SGM（説明書） | Auralyn（監査） | 追跡先 |
| --- | --- | --- | --- |
| 信号の流れ | 声だけの FX CHAIN → 配信全体の STREAM FX → LOUD が段として並び、どこに何がかかるかを位置で示す（p.6 図1、p.36） | 入力 → NR → 内蔵処理 → VST → 出力の流れが画面から読めない（B1）。詳細表示で「声を整える」が消える（A1） | #109 |
| 列と色 | 6列（伴奏入力・自分用の伴奏・配信・自分用の声・BGM・SE）に固有の色。「自分に聞こえる音」と「視聴者に届く音」を列で分ける（p.13） | 自分用と配信用の分離（#76／#77）は設定画面の中にあり、主画面からは見えない | #109 |
| メーター | dBFS、0〜−60dB を 6dB 刻み。−6dB まで列の色、−6〜0dB は黄、0dB 超は赤。直近1.5秒のピークホールド、一度でも 0dB に達すると残るクリップランプ（クリックで消える）（p.15） | 場所ごとに形と基準が違い、大型メーターは −3dB で「クリップ」表示（B2） | #108 |
| 遅延と動作方式 | ヘッダーに「ASIO・48k・…・RT xx.xms」を常時表示し、12ms 以下は緑、遅いと橙・赤。WASAPI ならそれも分かる。PANEL で ASIO ドライバーの設定画面を開く（p.7） | 段別の遅延（#28）は詳細表示の中。ヘッダーの状態表示には内部用語が出る（B6） | #108 |
| 初回の導線 | チュートリアルで光る所を順に設定し、OBS への送出・エフェクトの入れ方・保存まで約10分。練習用の素通しプラグインは終了後に自動で消える（p.6） | 毎日のホームが初回と同じ手順の形（A2）。入力の画面にメーターがない（A6） | #109 |
| ショートカット | Ctrl+Alt+Shift+1〜9 でプロジェクト、F1〜F9 で FX の段ごとのバイパス。登録に失敗するとボタンに「!」を出す（p.24） | ホットキー設定が隠しタブにあり、入力方式も古い（A5） | #110 |

Auralyn のほうが丁寧な点もある。緊急ミュート（SGM にはマイクのミュートボタンがない、p.32）、本番保護、適用前の保存と条件付きの取り消し、周囲の測定と同じ録音での NR 比較。SGM は説明書の注意書きで補っている（例：LEARN 中に声を出さない p.17、音量ミキサーでアプリをミュートしない p.9）。画面を軽くできれば、この丁寧さは Auralyn の強みとして残る。

## 2. 音楽鑑賞の位置づけ

PC の再生音（音楽・動画）に VST をかけて自分で聴く用途は、今回調べた2製品の範囲では空いている。

- **SGM**：FX CHAIN はマイクの声だけにかかる（p.19）。STREAM FX は配信の音だけにかかり、ヘッドホンの音にはかからない（p.36）。自分用の伴奏（INST MON）には VST をかける場所がない（p.13）。
- **Live Audio Assist**：OBS の中で動く製品で、OBS の外の再生音を自分で聴く用途は対象外（[LAA の比較](COMPETITOR_LAA_2026-10.md)）。

ただし Auralyn も、この用途の入口が弱い（監査 A3）。

- 再生音を入れるには、利用者が仮想ケーブル（Windows の出力 → CABLE Input → Auralyn）を自分で組む必要がある。Auralyn には再生音を直接取り込む入力がない（`loopback_probe` は経路の確認用）。
- セットアップの目的・画面の文言・既定値がマイク前提。配信用に NR や内蔵ボイスチェーンを有効にした人は、音楽にもそれがかかる。

Windows 全体の音に効果をかける既存のツールとの比較は行っていない。住み分けの判断は上記2製品との比較に限る。追跡先は #111。

## 3. 再生音の直接取り込み

SGM は、アプリ単位の取り込みを Windows 10 2004 以降で実用にしている（p.30）。説明書から分かる設計上の注意点は、Auralyn が同じ機能を検討するときの論点になる。

- 1アプリにつき最大16プロセス、同時に最大8アプリ。Chrome のようにタブごとに別プロセスで鳴らすアプリも、実行ファイル単位でまとめて取り込む（p.8〜9）。
- 取り込みは「横取り」ではなく「コピー」で、アプリの音は既定の出力からも鳴り続ける。二重に聞こえる場合、アプリの出力先を使っていない出力へ変え、その出力機器をミュートするよう案内している。アプリ単位のミュートは取り込みの音まで消えるため不可（p.9）。
- 音を出していないアプリは一覧に出ないことがあり、アプリを開き直すと数秒で自動的につなぎ直す（p.8〜9）。

Auralyn では、システム全体のループバックとアプリ単位のループバックのどちらを採るか、既存の入力 stream・rate 選択とどう統合するか、二重再生をどう案内するかを #111 の段階2で比較する。

## 4. 両書にない SGM の事実

- **OBS 連携プラグイン「sgm-audio-source」は GPL-2.0-or-later で公開**されている（p.40、[GitHub](https://github.com/norostudio000-bot/streamgearmixer-obs-plugin)）。GPL-3.0-only の Auralyn でも参考・利用できる条件である。ただし通信の取り決めは SGM 本体に合わせたもので、送る側は自作が必要。コードは未読。将来の D-03（OBS への直接送出）を検討するときの費用見積もりに使う。
- **本体は JUCE 製**（p.40）。VST がミキサーと同じプロセスで動くかは資料から分からない。
- **自社製プラグイン**：説明書の図に Stream Gear Tune／Processor／Effector が登場する（p.6 図1、p.36）。Processor はミキサー側の MON RVB と連動する（p.21〜22）。販売元のショップで公開中の商品は SGM のみ（2026-10-27 確認）で、「StreamGear シリーズ」として展開する様子。
- **自分用の音のために後段のプラグインを2つずつ起動する**（p.22）。追加照合の記録にある「複数起動できないプラグインでは調整不能」に加え、CPU 負荷が増える可能性がある（未確認）。

## 用途別の表示とウィンドウを設計する（2026-10-28追加）

配信・通話と音楽鑑賞では必要な表示が異なるため、用途ごとに最小サイズ・初期サイズ・最大化時の配置を設計する。配信側は900×600に収めることを必須とせず、必要な操作を置くための拡大を許容する。音楽鑑賞では現行サイズを候補に、小さい構成で成立するか確認する。寸法は未確定である。

### 今回の観察と現在の実装を区別する

SGM 1.0.0の実画面で、配信用と自分用の列、BGM・SEの送信量とモニター量、声用と配信用の別FX段、目的で探せるヘルプメニューを確認した。ASIO入力候補の一覧も確認したが、デバイス選択や音声送出は行っていない。SGMを際限なく縮小できる点と、Auralynの最大化時にVSTが途中までしか見えず余白が目立つ点は利用者の観察であり、こちらでは再現・原因特定していない。

Auralynの確認基準はローカルmain `78d9d70`。#108は実装済み・closed、#109はPR #117で状態帯・固定5段・1行ラックを部分実装、#110はPR #118で設定シートと1440px以上の2列配置を実装してclosed。#111はPR #120で用途追加と取り込み方式の調査まで進んでいる。実機合格とは区別する。上記の説明書調査と過去の比較表は当時の記録として残す。

現在のラック一覧には一定の高さに制限する指定を見つけていない。最大化時の問題は、使用ビルド・表示モード・VST数を固定して再現確認する。プラグイン独自GUIのサイズ制約と、Auralyn側のラック表示は分けて扱う。

### 表示内容を先に決め、寸法を検証する

| 用途 | 優先して見せるもの | サイズの判断 |
| --- | --- | --- |
| 配信・通話 | 入出力、送出状態、緊急ミュート、配信用／自分用の経路、メーター、VST | 必要な操作が無理なく成立するなら現行より大きな最小サイズも許容。通話に不要なOBS情報は常設しない |
| 音楽鑑賞 | 再生音の入力、出力先、音量、VST構成とGUIへの入口 | 配信向け情報を常設せず、900×600を含む小さい構成で操作を確認 |

- 表示用途は初回セットアップの目的から初期値を決めても、その後切り替えられるようにする。かんたん／詳細の情報量とは別に扱い、組み合わせを確認する。表示切替だけでNR・VST・機器・音量・送出・ミュートを変更しない。
- 用途ごとにサイズ・位置・最大化状態を記憶する。初回や既存の保存値がない場合の初期値を定義し、既存ユーザーの設定を無条件に上書きしない。
- 用途変更で最小サイズを下回る場合だけ必要な範囲を広げ、小さい用途に戻っても自動で縮めない。小さいモニターや高DPIで表示領域を超える場合は、配置変更・補助情報の折りたたみ・スクロールを併用する。主要操作を画面外へ閉じ込めない。
- 別モニターへの移動、DPI・解像度変更、最大化解除、再起動後にも、保存位置とサイズを現在の表示領域へ補正する。

### ラックと経路表示の受入条件を追加する

- [ ] 高さを増やすと一度に見えるVSTが増える。空き領域があるのに一覧だけを小さなスクロール領域に制限しない。横幅も用途に応じて活用する。
- [ ] 空／少数／多数VST、長い名前、通常／詳細表示で、末尾のVST・追加ボタン・GUI・並べ替えへ到達できる。サイズ変更で選択・フォーカス・スクロール位置を不必要に失わない。
- [ ] モニター分離中は、配信用と自分用の分岐・送り先・処理対象が分かり、各調整がどちらへ作用するかを操作前に確認できる。既存の調整画面へ移動できる。
- #109で同日に確定した「5段は状態確認と設定への入口」という仕様を維持する。分岐は既存情報の要約と調整先への入口で示し、全調整操作の移設や新規の経路図・ルーティング機能は追加しない。
- [ ] 停止・未設定・取得不能と正常な経路を区別する。内部の設定状態を、OBS・通話相手への音声到達確認にしない。
- [ ] 用途別に確定した最小サイズ・初期サイズと、1280×720・1920×1080・2560×1440で確認する。900×600は現行比較と音楽鑑賞側の候補として残し、全用途の固定下限にはしない。表示領域が不足する条件、日英、キーボード、実DPIも含める。
