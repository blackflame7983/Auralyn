# バージョンとリリースの判断基準

制定日: 2026-10-15。今後のリリースに適用し、公開済みの番号・タグ・履歴は変更しない。

## 基本方針

[Semantic Versioning 2.0.0](https://semver.org/) を基礎に、Auralyn の利用者が依存する互換性を判定する。
安定版は `MAJOR.MINOR.PATCH`、Git / GitHub Release のタグは `vMAJOR.MINOR.PATCH`。
例: アプリ `1.2.3`、タグ `v1.2.3`。日付、コミット数、変更行数、作業期間では決めない。
1リリースに含む全変更を評価し、必要な最大の変更区分を1回適用する。

| 区分 | 判定 | 1.2.3 からの例 |
| --- | --- | --- |
| major | 既存の互換性を破る。既存データを移行できない、対応機能・環境を削除する、利用者が設定し直さなければ従来の用途で動かない | 2.0.0 |
| minor | 互換性を保つ機能追加、明確な機能改善、機能の非推奨化 | 1.3.0 |
| patch | 互換性を保つ不具合・セキュリティ修正、安定性や性能の改善、配布バイナリの軽微な文言修正 | 1.2.4 |
| none | 文書・テスト・開発手順のみで、利用者へ新しい配布物を出す理由がない | 番号変更・タグなし |

ビルド依存更新だけなら `none` を基本とする。実行時依存や配布物を修正して再配布するなら、互換性を確認したうえで最低 `patch`。
依存ライブラリの major 更新が、Auralyn の major 更新を自動的に意味するわけではない。
機能を増やさない内部リファクタリングは、配布理由がなければ `none`、配布する安定性改善なら `patch`。
未検証の互換性を「維持」と断定しない。判定保留とし、必要な確認を示す。

## Auralyn で守る互換性

これはライブラリ API だけでなく、次の利用契約を含む。

- 保存データ: `.auralyn-preset.json`、フルプロファイル、プラグイン状態、localStorage の設定・復元。
- 音声: 既存の WASAPI / ASIO 入出力、対応サンプルレート・チャンネル、ゲイン・バイパス・ルーティングの意味と既定値。
- プラグイン: 対応 VST3 のロード・状態復元・操作。互換性を約束した対応範囲を縮小しない。
- 環境・配布: サポート対象 Windows、更新経路、インストール先・アプリ識別子、設定の引継ぎ。
- 連携: サポート対象 OBS との連携。内部 JSON-RPC は同梱ホストとエンジンを揃えて配布する限り、それ自体の変更だけで major にはしない。

内部フォーマットの `schemaVersion` はアプリのバージョンとは別に管理する。
新スキーマでも既存データを損失なく自動移行し、従来用途を保てるなら minor にできる。
手動での作り直しやデータ損失が必要なら major。旧版へ戻せない場合は必ず明示し、移行前バックアップを用意する。
意図的な音色・ゲイン・レイテンシ設定の意味の変更は、既定で既存の配信へ影響しないか評価する。
仕様どおりへ戻す不具合修正は通常 patch だが、結果の音が変わる場合はリリースノートへ明記する。
UI の見た目の変更だけで major にしない。操作経路や対応機能の喪失がある場合は別途評価する。

## 例

| 改修内容 | 通常の判定 | 確認事項 |
| --- | --- | --- |
| デバイス再接続時のクラッシュ修正 | patch | 再接続・再起動・音声継続 |
| 既存設定を保った音声診断機能の追加 | minor | 既存経路の音声・設定復元 |
| 旧プリセットを読めなくする形式変更 | major | 移行方針とデータ退避 |
| 旧プリセットを読めるプロファイル拡張 | minor | 実際の旧版データの読込み |
| 対応 Windows / ASIO / VST3 の一部を廃止 | major | 対象ユーザー・代替経路 |
| CPAL / rubato の置換 | 保留 | API差分だけではなく音質・遅延・デバイス互換性を確認後に決定 |
| README と AI 作業ルールの整理 | none | 配布物変更の有無 |

## AI が提案する手順と形式

1. 前回の公開安定版を公開履歴・タグ・公開記録で特定する。最新ローカルタグだけを公開済みと断定しない。公開先を確認できない場合は、その限界を示す。
2. 基準タグと対象コミットを記録し、`git log <tag>..HEAD`、`git diff <tag>..HEAD` と今回の未コミット差分も含めて調べる。リリース未収録の変更を漏らさない。
3. 各変更を major / minor / patch / none / 保留 に分類し、上記の互換性項目に証拠を対応させる。`feat:` や `BREAKING CHANGE:` は調査の手掛かりであり、最終根拠ではない。
4. 最大区分から候補番号を計算する。minor なら patch を0、major なら minor / patch を0にする。現行ファイルが次期番号でも、その番号から二重に上げない。
5. ユーザーへ次の形式で提案する。番号の反映依頼と、タグ・公開の許可は別に扱う。

```text
基準: v1.1.0（公開記録の確認先、基準SHA）
対象: 対象SHA、未コミット差分の有無
候補: 1.1.1 / タグ v1.1.1（または none / 判定保留）
判定: patch
理由: 変更ごとの区分と、最大区分を選んだ根拠
互換性: 保存データ、音声、プラグイン、対応環境、連携への影響
検証: 実行結果、実機未確認、残る課題
リリースノート案: 利用者に見える変更、移行・既知の制限
```

## 番号の反映とタグ

- バージョンの正本は `package.json`。同期先は `package-lock.json`（ルートと `packages[""]`）、`src-tauri/tauri.conf.json`、`src-tauri/Cargo.toml` の `[package]`、`src-tauri/Cargo.lock` の `vst-host`。
- `npm run set-version -- 1.2.3 --dry-run` で確認し、反映依頼後に `npm run set-version -- 1.2.3`。`npm run set-version -- --check` で不一致を検出する。
- 同期処理は依存解決・コミット・タグ作成・公開を行わない。公開履歴や過去のアーカイブ名も書き換えない。
- `npm run release:check` と変更範囲に応じた検証を実行する。バージョン変更だけでリリース準備完了とは扱わない。
- 公開版と同じ番号で成果物を差し替えない。再ビルドして再配布する場合も新しい patch 以上を使う。公開済みタグの付け替えや強制 push をしない。
- 承認されたリリースコミットに注釈付きタグ `vX.Y.Z` を付ける。公開先の Release タグと、Source manifest の元コミットを一致させる。タグ作成と push はそれぞれ許可された範囲で実施する。
- `latest.json` の `version`、インストーラー、Portable、Source ZIP は同じ番号・同じコミットに揃える。公開後は取得した manifest・チェックサム・更新経路も確認する。

## 検証版と緊急修正

SemVer の `-alpha.N` / `-beta.N` / `-rc.N` は将来の検証版の候補形式とする。
現行運用は安定版の3桁のみを受け付ける。検証版は、Windows installer の扱い、GitHub prerelease、別の更新経路、安定版への遷移を検証してから導入する。
安定版用 `latest.json` に検証版を混ぜない。`+build` は更新順に影響しないため、再配布の番号として使わない。
[Tauri Updater](https://tauri.app/plugin/updater/) は既定で現在より新しい版を更新候補とする。
ロールバックは古いタグの差し替えではなく、直前の安定動作へ修正した新しい patch を公開する。破壊的変更を含むなら major 基準を維持する。
