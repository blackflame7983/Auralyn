## 推奨実装順序

```
フェーズA: 1 → 2   （録音基盤 → 分析。共通インフラで一体開発）
フェーズB: 4 → 5   （既存資産の拡張。小〜中規模）
フェーズC: 6        （随時。2の結果を反映しながら）
フェーズD: 3        （最大工数。A〜Cの成果を前提に判断）
```

## 計画作成時の追加提案（元テーブルからの変更点）

1. **プラン1と2は共通の「録音・分析パイプライン」として設計**する。
   エンジン側に Pre/Post 同時キャプチャの仕組みを1回作れば、Before-After 試聴（プラン1）と
   品質指標算出（プラン2）の両方が乗る。別々に作ると録音経路が二重になる。
2. **プラン3は「OBS プラグイン」単体ではなく、先に軽量な代替案（OBS 側 WebSocket 経由の
   自動セットアップ）を挟む**ことを推奨。既存の `obws` 連携を使い、OBS に音声入力キャプチャ
   ソースを自動作成するだけで「仮想ケーブル設定で迷う」問題の大半は解消できる。
   ネイティブプラグインは工数・保守コストが桁違いなので、フェーズDで再評価。
3. **プラン4は新規機能ではなく既存 `TroubleshootModal` の「実測ベース化」**と位置づける。
   現状は名前マッチ中心の静的チェックのため、信号を実際に流して検出する方式に強化する。
4. **プラン5は既存の `.auralyn-preset.json` を v2 スキーマに拡張**し、後方互換を維持する。
   新形式を別に作るとインポート/エクスポート導線が分裂する。
