# R1：自動の再開の制限（洗い出しと最小の設計案）

> 状態：案（2026-11-24。コードは変えていない）。正本は今のコード（main 79741173）。`audio-session-controller.md` の12章は「案」で、そのとおりに作る必要はない。
> 方針（利用者の指示、2026-11-24）：作り込みすぎない。まれな場面のために作らない。迷ったら小さい方。F1b は独立の段にしない（J-27）。

## 1. 今の自動の再開の流れ

フロントだけが持つ。Rust は再開を知らず、再開の Start は通常の `start_audio` として入る。

| 段 | 内容 | 場所 |
| --- | --- | --- |
| きっかけ | 子から `Error` が来ると `audio-stream-error` が出る。本文に `Stream Error` を含むものだけ拾う | `src-tauri/src/audio/reader.rs:101-109`、`src/hooks/useAudioRecovery.ts:28-29` |
| 入る条件 | 再開中・上限到達済みでない、`reviewOnly` の一時セッションでない、確認待ち（`REVIEW_KEY`）でない、保存設定がある | `useAudioRecovery.ts:29-32` |
| 設定の控え | その時点の `localStorage` の保存設定（`vst_host_audio_config`）を JSON で控える。再開に使う設定もこれ | `useAudioRecovery.ts:31-33` |
| 予約 | 警告の通知の後、1回目は2秒後、失敗するたびに4秒・6秒後（`attempt * 2000`） | `useAudioRecovery.ts:38-40, 84-87` |
| 実行 | 時間が来たら、控えが今の保存設定と違えば止める。違わなければ `liveModesApi` の snapshot を取り、保護中（armed）なら実際の設定を取り、`audioApi.start`（`start_audio`）を呼ぶ | `useAudioRecovery.ts:41-62` |
| 回数 | 失敗するたびに次を予約し、3回目の失敗で打ち切る（`exhausted`、エラー通知）。再開中の重複通知は無視する。上限の後は、再開中でないときの `audio-started` まで再開しない | `useAudioRecovery.ts:29, 72-82, 89` |
| 成功 | `start` の応答で成功の通知を出す | `useAudioRecovery.ts:70-71` |

**止まり方**

- 手動の停止：Rust の `Stop` は、子が生きていれば必ず `audio-stopped` を出す（`audio_engine/core.rs:1421-1429`）。フロントは `audio-stopped` で予約を取り消す。ただし**自分の Start の最中に来た停止通知は無視する**（失敗した Start も `Stopped` を出すため。`core.rs:1328-1333`、`useAudioRecovery.ts:90-93`）。
- クラッシュ（`audio-error`）：取り消して上限扱い（`useAudioRecovery.ts:94`）。
- 設定の変更：**予約が実行される時点で**、保存設定が控えと違えば取り消す（`:43-47`）。変更した瞬間には取り消さない。
- 手動の開始：**取り消さない**。`audio-started` は `exhausted` を戻すだけで、予約は残る（`:89`）。
- 確認のセッション：見るのは `reviewOnly` と `REVIEW_KEY` だけ。ボイスチェック等の確認の音声は見ていない。
- Rust 側の守り：`start_audio` は `JobClass::Starting`。**停止より前に受け付けた Start は、取り出す時に断る**（`StoppedFirst`。`control/class.rs:47-51, 140`、`control/queue.rs:180-181, 395-398`）。停止の後に受け付けた Start は断られない。
- 動いているところへ Start が入ると、ストリームを同じ設定で作り直す（`audio_engine/core/startup.rs:418-423`）。

## 2. 実際に起きうる問題

| # | 順序 | 起きやすさ | 利用者から見た害 | main で今起きるか |
| --- | --- | --- | --- | --- |
| P1 | 障害 → 待ち中に手動の停止 | ふつう | なし | **起きない**。`audio-stopped` で取り消す（`useAudioRecovery.ts:90-93`）。待ち（snapshot・実設定の取得）の途中でも `valid()` で戻る（`:42, 50, 54`）。試験あり（`useAudioRecovery.test.tsx:31`） |
| P2 | 障害 → 待ち中に利用者が手動の開始（同じ設定）→ 予約が残る → 時間が来て2回目の Start | ときどき（障害の直後2〜6秒以内に自分で開始したとき） | 動いている音が張り直され、短く途切れる。不要な「再接続しました」の通知。設定は変わらない | **起きる**。開始で取り消さない |
| P3 | 障害 → 待ち中に手動の開始（違う設定） | ふつう | なし | **起きない**。保存設定が控えと違い、実行の冒頭で取り消す（`:43-47`）。残る窓は、冒頭の確認から Start の受付までの snapshot 取得中の数ms〜数十msだけ（きわめてまれ） |
| P4 | 再開の Start が Rust の列で長い操作の後ろに待っている間に停止 → 停止が先に走り、Start は `StoppedFirst` で断られる → 停止の通知は「自分の Start 中」として無視され、失敗として次を予約 → 2〜6秒後に音が鳴る | まれ（再開の Start の受付〜実行の間に長い操作が前にあり、その間に停止したとき） | **停止したのに、数秒後に音が勝手に鳴る** | **起きうる**。Start が実行中なら停止はその後に走る（J-22）ので、成功すれば停止され、失敗しても停止の通知が自分の Start の外に来れば取り消せる。害が出るのは上の順序だけ |
| P5 | 予約の実行の直後（snapshot 取得の最中）に停止の通知が届く | きわめてまれ | 起きない（`valid()` で戻る）。Start を呼んだ後の数msに届くと P4 と同じ | P4 と同じ形。直し方も同じ |
| P6 | トレイ・ショートカット・予定など Rust 側の停止が、P4 の窓に重なる | きわめてまれ | P4 と同じ | 起きうる。フロントが数える手動の停止に含まれない。既知の制限として扱う |
| P7 | 確認の音声（ボイスチェック等）が動いている間の再開 | 障害でストリームが死んだ時点で確認も止まっており、再開が壊す物はない（実機の確認は未実施） | — | 確認のセッションは F2 で Rust に入る。R1 では扱わない |
| P8 | 障害の通知が遅れ、手動の Start B の後に古い予約が再開（計画12.1の順序） | まれ | B が成功すれば P2。B が失敗して止まっていた場合は、保存設定が同じなら再開が走るが、直前に動いていた設定を戻すだけで、害ではない | 上のとおり |

ふつうに起きて害のあるものは**ない**。P2 は起きるが害は小さい。P4 は害が大きいが、まれな順序でだけ起きる。

## 3. 最小の直し方の案

### 結論

Rust の `RecoveryAuthority`・`recover { authority_id }`・番号の照合は入れない。

- 古い再開の予約の出どころは、フロントのタイマー1つだけで、フロントで取り消せる。
- 「停止より前の Start は断る」は、すでに Rust にある。足りないのは、フロントが**断られた後に再び予約する**ことだけ（P4）。
- 今、Rust から始める再開はない。

### 案A（推奨）：フロントだけの2点

1. **手動の開始で取り消す。** `audio-started` が来たとき、自分の Start の最中でなければ（`startingGeneration !== generation`）`cancel()` する。P2 を消す。`audio-stopped` の既存の判定と同じ形（`useAudioRecovery.ts:92`）。
2. **手動の停止を、自分の Start の最中でも見分ける。** `audioApi.stop()` の呼び出し回数を数えるだけの変数を `src/api/audio.ts` に持ち（呼ぶ時点で数える）、フックは障害の通知の時点の値を控える。Start が失敗して再予約する前と、予約の実行の冒頭で、値が変わっていたら `cancel()`。P4・P5 を消す。`StoppedFirst` の文言には頼らない。

| 項目 | 内容 |
| --- | --- |
| 変えるファイル | `src/hooks/useAudioRecovery.ts`、`src/api/audio.ts`（数える変数と読み出し。数行）、`src/hooks/__tests__/useAudioRecovery.test.tsx`。**3ファイル**。Rust は変えない |
| 試験（継ぎ目で順序を固定。sleep なし。既存の `notify`・`tick`・Promise の手動の解決の型） | (a) 予約の待ち中に `audio-started` を通知 → 時間を進めても `start` を呼ばない。(b) 再開の Start の応答を Promise で保留 → `audioApi.stop()` → 自分の Start 中の `audio-stopped` を通知 → Start を reject → 時間を進めても次の `start` を呼ばない。**新しい試験2つ**。既存の「自分の Start の通知では取り消さない」（`:51`）は変えずに通ること |
| 利用者から見て変わること | 障害の直後に自分で開始したとき、同じ設定の2回目の開始と「再接続しました」の通知がなくなる。停止した後に音が勝手に鳴ることが、まれな順序でもなくなる。何もしないときの再開は同じ |

状態遷移：障害 → 警告・予約（2秒）→ 実行 → 成功で終わり／失敗なら次を予約（4秒、6秒）→ 3回失敗で上限。どの待ちでも、手動の開始・手動の停止・設定の変更・クラッシュで取り消して終わる。

### 案B（入れない）：計画12章のとおり

Rust に権限・`recover`・`manual_epoch`・停止の番号を持たせる。Rust 側の停止（P6）も消せるが、確定点・`manual_epoch`・版つき通知といった F1b の部品が先に要り、まれな害のために規模が大きい。

### 案C：何もしない

P2 の害は短い途切れと余分な通知だけ。ただし1点目は数行で済み、試験も1つなので、案A の1点目だけでも入れる価値はある（2点目が不要と判断するなら、1ファイル・試験1つ）。

## 4. 要承認の候補

なし。案A は、手動の開始・停止があれば再開をやめる、という**今の動きを狭める**だけで、何もしないときの再開は変わらない。

報告：
- 手動の開始・停止の後に、古い再開の予約が動かなくなる（案A）。
- 計画12章の `recover`・権限、「origin なしの `start_audio` は手動の開始」の扱いの変更は、入れない。`start_audio` の受付は今のまま。

## 5. R1 自体が要るか

**Rust 側の R1（権限・`recover`）は不要。既知の制限として記録する。** 残るのは、Rust 側の停止が再開の Start の最中に重なる場合（P6）と、確認のセッションとの関係（P7、F2 で扱う）。フロントの小さな直し（案A）は、R1 の段として独立させず、1つの小さな PR で入れればよい。
