# デザイン刷新の実装計画（2026-11-12 作成）

[DESIGN.md](../DESIGN.md) 10章の規則を、製品の画面へ段階的に実装する計画です。
この文書は計画であり、実装済みや検証済みの証拠ではありません。

- 規則の正本：`docs/DESIGN.md` 10章
- 経緯と試作：[DESIGN_RENEWAL_2026-11-12.md](../DESIGN_RENEWAL_2026-11-12.md)、`?proto=g2`（開発時だけ）
- 設定項目の置き場所：[settings-inventory.md](../verification/design-renewal-2026-11-12/settings-inventory.md)

## 1. 進め方

- 1段階を1つの PR にする。PR は積み上げず、前の段階が main に入ってから次のブランチを main から作る。
- 設計と依頼文、結果の確認と、実装は、担当を分ける。どの道具に任せるかは利用者の指示に従い、この文書には固定しない。
- 各段階で、規則と食い違う既存の節（`DESIGN.md` 10.11 の表）と、利用者向けドキュメントの該当箇所を同じ PR で直す。
- 音声エンジン、IPC、音声コールバックは変えない。変える必要が出たら、その段階を止めて相談する。
- 試作（`src/prototypes/`）は見本として読む。製品へコピーせず、既存の共通部品（Button、SegmentedControl、Slider など）とトークンで作る。試作のクラス名（`oa-*`、`rn-*`）を製品へ持ち込まない。

**前提**：ブランチ `codex/design-renewal-2026-11-12`（規約と試作）が main に入っていること。

## 2. 段階の順

| 段階 | 内容 | 終わると変わること |
| :--- | :--- | :--- |
| A | 右に本番中の操作の列を作り、緊急ミュート・出力音量・VST を外して比較を移す。フッターをなくす | 本番中の3操作が1か所にまとまる |
| B | ホームを刷新する（いまの状態と主操作、音の流れの帯、3枚のカード）。入出力メーター、マイク音量、操作ロックを右の列へ移す。大型メーターをなくす | 第一印象が変わる |
| C | 左のレールと上の帯を作り、ヘッダーをなくす | 外枠の3列がそろう |
| D | 「接続」をページにする（現行の設定「オーディオ」）。設定をモーダルからページにする | 設定中も本番中の操作が見える |
| E | 「音づくり」をページにする | 設定は4区分になる |
| F | 「VST」をページにし、右パネルをなくす | |
| G | ゲーミングの形を変える | |
| H | 窓が大きいときの表示（ホームの2段目、接続の列、全体の拡大） | |

**レールを最初にしない理由**：現行のホームは、音調整の3連モジュールが、音調整の内側の幅で1列に切り替わる。レール（76px）と右の列（212px）を同時に入れると、中央が大きく狭まり、既定の 1024×768 でも3列の余裕がほとんどなくなる。そのため、ホームを先に刷新してから（B）、レールを入れる（C）。

**段階 A の実装で分かったこと（2026-11-12）**：切り替えの境目は、文書では780pxと書かれていたが、実装は内側の幅720pxだった。右の列を入れると、配信・通話の最小 960×640 で内側の幅が666pxになり、1列に切り替わって3つ目が画面の下へ回った。段階 A で境目を660pxに下げ、最小サイズでも3列を保つようにした。この境目のまま C でレールを入れると、1024×768 の内側の幅は約664pxで、余裕は4pxしかない。C の前に B でホームを刷新する順は変えない。

**段階 A で残した点**：幅1200px以上で右パネルをホームの横に並べる境目は変えていない。右の列の分、幅1200〜1411pxでパネルを開くと中央が以前より212px狭く、幅1222〜1374pxでは音調整が1列になる。境目を1412pxへ上げるか、右パネルがなくなる段階 F まで残すかは、利用者の判断を待つ。

D〜H の詳細は、前の段階の結果を見てから書く。

## 3. 段階 A：右の本番中の操作の列

### 3.1 目的と範囲

**置き場所を移すだけにする。** 見た目の新しい部品（横向きのメーター、「適正」の一言など）は入れない。それらは B で扱う。

| 操作・表示 | いまの場所 | A のあと |
| :--- | :--- | :--- |
| 緊急ミュート | ヘッダーの右（`Header.tsx`） | 右の列の一番上 |
| 出力音量（`OutputGainControl`） | フッター（`MasterBar.tsx`） | 右の列 |
| 未設定のときの出力メーター（`MasterOutputMeter`） | フッター | 右の列。出す条件は変えない |
| VST を外して比較（`#ab-compare-btn`） | フッターの左（`AppShell.tsx`） | 右の列。出す条件は変えない |
| 処理の停滞・統計を取得できない旨の表示、音切れの印、音声処理の詳細の入口 | フッター（`MasterBar.tsx`） | 右の列の一番下 |
| フッター | あり | なくす |

A で動かさないもの：ヘッダーのそのほか（ロゴ、状態、設定、ヘルプ）、本番帯（入出力メーター、マイク音量、操作ロック、歌／雑談）、音調整、右パネル、大型メーター、設定のモーダル。

【設計で足した点】フッターにある「処理の停滞」などの表示と「音声処理の詳細」の入口は、試作に置き場所がなかった。A では右の列の一番下に置く。C で上の帯を作るときに、置き場所を見直す。

### 3.2 配置

- `AppShell.tsx` の `.workspace-body`（ホームと右パネルを入れている行）の右隣に、`<aside aria-label="本番中の操作">` を置く。ヘッダーの直下から窓の下端まで。通知の行は中央の列の中に置き、通知が出ても右の列を動かさない（最初の計画では「通知の行の下」としていたが、緊急ミュートを押すと出る通知で列が下へ動くため、PR 前のレビューを受けて直した）。
- 幅は212pxで固定する。背景は `card`、左に境界線1本。
- 右パネルの重ね表示と暗幕は、これまでどおり中央の作業領域だけを覆う。右の列は覆わず、操作できるままにする。
- 列の中は上から、緊急ミュート、出力（メーターを出す条件のときはメーター、出力音量）、VST を外して比較、余白、状態の表示と詳細の入口。
- 列は縦にスクロールさせない。用途別の最小サイズ（配信・通話 960×640、音楽鑑賞 900×600）で、全部が見えること。
- 出力音量は、ラベルと値の行、スライダーの行の2行に組み替える。「100%へ戻す」と再試行、ミュート中の出力確認の入口は残す。
- 広い窓で中央へ寄せる計算（`index.css` の `.workspace-body` の `max-width`）は、右の列の幅を足して直す。右の列は窓の右端に付ける。

### 3.3 変えてはいけないもの

- 緊急ミュートの動作：押した瞬間の見た目と文言の切り替え、失敗時のトーストと設定の入口、ホットキー、`aria-pressed`、名前は固定で状態は別に示すこと（`DESIGN.md` 2.5、3.3）。
- VST を外して比較：`role="switch"`、`aria-checked`、比較中の「VST オフ」の表示、`id="ab-compare-btn"`、`global-bypass-changed` の購読。
- 出力音量：`focusOutputGain()` で外からフォーカスできること、即時反映、失敗時の表示と再試行。
- `homeChrome.ts` の出し分けの条件（未設定のときは比較を比較中だけ出す、など）。名前は `footer` から変えてよいが、条件は変えない。
- 文言キー。新しい文言が要るのは `aside` の名前だけの見込み。ja と en を同時に足す（`DESIGN.md` 3.7）。
- 共通部品の見た目。文字・角丸・動きは役割のトークンを使い、`uiConsistency.test.ts` の上限を増やさない。

### 3.5 完了の条件

1. 緊急ミュート、出力音量、VST を外して比較が右の列にあり、同じ操作がほかの場所にない。
2. フッターがない。
3. 960×640、900×600（音楽鑑賞）、1024×768、1920×1080 で、右の列の全操作が画面内に見え、文字の切れ・重なりがない。
4. 右パネルを重ねて開いた状態で、右の列の3操作が押せる。
5. 緊急ミュートのホットキー、比較のホットキー、出力音量へのフォーカス移動が、移動前と同じに動く。
6. 3テーマ（オーロラ、ライト、ゲーミング）で、文字4.5:1、状態の目印3:1 を保つ。
7. Tab の順が、ヘッダー → 中央 → 右の列、または合理的に説明できる順になっている。順を PR の説明に書く。

### 3.6 確かめ方

実装した側が実行して、結果を PR の説明に貼る。

```bash
npx tsc --noEmit -p .
```

```bash
npm run test:unit
```

```bash
npm run test:dom
```

```bash
npm run test:e2e
```

```bash
npm run test:user-docs
```

次の3つは、CI（`.github/workflows/frontend-quality.yml` の `checks`）が行う確認。上の5つでは代わりにならないので、push の前に必ず実行する。段階 B 以降も同じ。

```bash
npx tsc --noEmit -p tsconfig.e2e.json
```

```bash
npm run test:release
```

```bash
npm run release:check
```

- `e2e/browser/` の試験の型は、1つ目でだけ検査される。段階 A では、これを手元で実行しておらず、足した試験の型の読み込み元の誤りを CI で初めて見つけた（PR #520）。
- `npm run test:release` は PowerShell で実行する。Git Bash では `tar` が Windows のパスを扱えず、変更と関係なく2件失敗する。
- CI の `browser` は、`npx vite build` のあと本番ビルドを配って2並列で試験する。手元の `npm run test:e2e` は開発サーバーで直列なので、同じ条件ではない。本番ビルドでだけ出る失敗を疑うときは、`npx vite build` のあと `E2E_PREVIEW=1` を付けて `npm run test:e2e` を実行する（`playwright.config.ts`）。
- CI の手順が変わっていないかは、段階ごとにワークフローのファイルで確かめる。
- Rust は変えないので、`cargo` の確認は不要。変えた場合は `docs/BUILD_GUIDE.md` の手順を足す。
- 画面は、開発プレビュー（`?mock=live-home`、`stopped-home`、`first-run`）のスクリーンショットを、完了の条件3の4サイズ × 3テーマのうち代表で撮る。保存先は `docs/verification/` の下に段階ごとのフォルダーを作る。
- 実機（Tauri）の確認は Claude か利用者が行う。**起動すると保存済みの設定で音声処理が自動で始まる**（2026-11-12 に確認）ので、利用者の了解を取ってから、時間を短くして行う。
- 実際の音での確認、表示倍率150%、長時間の動作は、この段階では未確認として PR に書く。

### 3.7 依頼するときの注意

- 作業は main から作った専用のブランチ（`codex/renewal-a-safety-column`）で行う。push と PR 作成はしない。
- 既存の未コミット・未追跡のファイルに触れない。`git add .` を使わない。
- 範囲の外（3.1 の「A で動かさないもの」）に手を入れない。直したい点を見つけたら、変えずに報告する。
- 試験を通すために、既存の試験の期待を緩めない。場所が変わった分だけを直し、直した理由を書く。
