# プラン6: 機能表現・期待値調整

## 目的

UI / LP（`docs/WEB_SITE_DESIGN.md` ベースのサイト）/ ドキュメントの表現を
実際の性能に合わせ、「期待外れ」による失望と低評価を防ぐ。
特に AI ノイズ抑制（RNNoise 系 = nnnoiseless）は Krisp や NVIDIA Broadcast と
同等の分離性能ではないため、誇張を避けつつ強みを正しく伝える。

## 方針: 表現ガイドラインの策定 → 全文言の棚卸し → 修正

### ステップ 1: 表現ガイドライン策定（成果物: `docs/COPY_GUIDELINES.md`）

原則案:

| 原則 | NG 例 | OK 例 |
|------|-------|-------|
| 効果は対象を限定して書く | 「あらゆるノイズを除去」 | 「ファン・空調などの持続的なノイズを低減」 |
| 消えないものを明記する | （無記載） | 「周囲の会話や BGM は完全には消えません」 |
| 断定より体感確認へ誘導 | 「プロ品質の声に」 | 「ボイスチェックで効果を確認できます」（プラン1 連携） |
| 数値は実測根拠があるものだけ | 「ノイズ −40dB」 | プラン2 の実測値をユーザー環境で表示 |
| トレードオフを隠さない | 「遅延ゼロ」 | 「約 XX ms の遅延が発生します（画面に実測表示）」 |
| 「AI」の濫用を避ける | 「AI が声を完璧に」 | 「機械学習ベースのノイズ低減（RNNoise 系）」 |

既存の `docs/CODING_GUIDELINES.md`（日本語 UX 指針）と `PROPOSALS_AI_NOISE_HOST.md` の
注意文方針（「BGM や周囲会話を完全に消すものではない」）を統合・昇格させる。

### ステップ2: 文言の棚卸し（インベントリ作成）

対象を全数リストアップして、ガイドライン適合を ○/× 判定する表を作る:

- **UI 文言**: `src/` 内の日本語文字列
  （主対象: `AudioSettingsModal.tsx`, `MasterBar.tsx`, Setup Wizard, Tutorial,
  TroubleshootModal, テンプレート説明文 `templates/chainTemplates.ts`）
- **LP/サイト**: `docs/WEB_SITE_DESIGN.md` およびサイト実体のコピー
- **README / ストア説明 / リリースノート**

棚卸し結果は `docs/plans/PLAN_06_COPY_INVENTORY.md`（実施時に作成）へ。

### ステップ 3: 修正実装

- 優先度 1（誤解が実害になる箇所）:
  - ノイズ抑制の効果範囲（効く対象/効かない対象の明記。設定モーダルに常設の注意文）
  - 遅延に関する表現（実測レイテンシ表示は既存機能なので「実測を見せる」方向に寄せる）
  - Venue Mode / Smart Learn の説明（「学習」= 定常ノイズのプロファイリングであることを明示）
- 優先度 2:
  - Setup Wizard・チュートリアルの導入文（過度な簡単さの約束をしない。
    仮想ケーブルが必要なケースを最初に伝える → プラン4 の診断へ接続）
  - テンプレート名・説明（「プロ級」等の形容を効果ベースの説明に置換）
- 優先度 3: LP の見出し・機能表。**プラン2 完成後は「あなたの環境での実測値」を
  見せる UI が最強の期待値調整になる**ため、静的コピーは控えめに保つ。

### ステップ 4: 再発防止

- `COPY_GUIDELINES.md` を `docs/CODING_GUIDELINES.md` から参照させ、
  新機能の文言レビュー項目に追加する。
- 将来的に文言を i18n リソース化するかは本プラン外（現状は日本語ハードコード）。

## 実装フェーズ

| フェーズ | 内容 | 完了条件 |

| 6-a | COPY_GUIDELINES.md 策定 | 原則表 + NG/OK 対訳が揃う |

## 他プランとの連携

- プラン1（ボイスチェック）: 「聴いて確認できます」が最も誠実な訴求になる。
  文言からの導線を必ず張る。
- プラン2（品質指標）: 宣伝上の数値を、ユーザー自身の環境での実測表示に置き換えられる。
- プラン4（診断）: 「簡単セットアップ」と言う代わりに「つまずいたら診断で解決」を提示。

## テスト・検証

- コードではなく文言変更が主のため、レビュー観点チェックリスト
  （ガイドライン適合・導線の有無）で PR レビューする。
- 可能なら初見ユーザー 2〜3 名に Setup Wizard を通してもらい、
  「期待と違った点」をヒアリング（`UX_CRITIQUE.md` の手法を踏襲）。
