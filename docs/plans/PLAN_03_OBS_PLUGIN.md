# プラン3: OBS プラグイン化（+ 先行代替案）

## 目的

OBS に「Auralyn Processed Mic」音声ソースを追加し、OBS ユーザーが仮想ケーブル
（VB-CABLE）なしで加工済みマイク音声を取り込めるようにする。

## 提案: 2 段構えにする（元案からの変更提案）

ネイティブ OBS プラグインは工数・配布・保守コストが最も重い。
そこで **段階 A（軽量・既存資産の延長）を先に出し、段階 B（本命プラグイン）は
段階 A の利用状況を見て投資判断**することを推奨する。

### 段階 A: OBS WebSocket による自動セットアップ（推奨・先行）

既存の `obws` 連携（`src-tauri/src/obs.rs`）を拡張し、ワンクリックで:

1. OBS 内に「Auralyn マイク」音声入力キャプチャソースを自動作成
   （デバイス = 仮想ケーブルの CABLE Output を自動選択）
2. 既存の重複マイクソースをミュート提案（誤って生マイクと二重取りする事故を防止）
3. モニタリング設定・同期オフセットの推奨値を自動適用
4. 接続確認: Auralyn 側でテストトーン → OBS の入力レベルを WebSocket で読み、
   実際に音が届いているかを検証（プラン4 の診断と共通化）

- 仮想ケーブル自体は残るが、「OBS 側の設定で迷う」問題は解消される。
- 工数: 小〜中。リスク: 低。OBS 28+ (obs-websocket 5.x) 前提。

### 段階 B: ネイティブ OBS プラグイン「Auralyn Processed Mic」

#### アーキテクチャ選定

| 案 | 内容 | 評価 |
|----|------|------|
| B-1 | プラグインが Auralyn エンジンと**共有メモリ/ローカルソケットで PCM 受信**する音声ソース | ◎ 推奨。エンジンは単一プロセスのまま、OBS はコンシューマ |
| B-2 | プラグイン内に処理エンジンを丸ごと埋め込む | × VST ホスティングや UI と分裂。保守不能 |
| B-3 | 仮想オーディオドライバを自作 | × 署名・カーネルドライバの負担が過大 |

**B-1 を採用**。Auralyn 側に「タップ出力」を追加し、加工後 PCM を
共有リングバッファ（named shared memory + イベント）へ発行。
OBS プラグイン（Rust `libobs` バインディングまたは C++ obs-plugintemplate）は
それを読む audio source として登録する。

#### 必要な作業

1. エンジン: 加工後 PCM のブロードキャストタップ（プラン1 の録音タップと同系統の機構を再利用）
2. IPC/プロトコル: 共有メモリのフォーマット定義（サンプルレート・ch・シーケンス番号・
   underrun 検出）。Auralyn 停止時の無音フォールバック
3. OBS プラグイン本体: ソース登録、プロパティ UI（接続状態表示のみの最小構成）、
   Auralyn 未起動時の案内
4. ビルド・配布: プラグイン用の別ビルドパイプライン（OBS SDK 依存）、
   インストーラで `obs-studio/obs-plugins/64bit` へ配置、OBS バージョン互換マトリクス
5. Auralyn 側 UI: 「OBS 連携」設定画面にプラグインのインストール/状態確認を追加

#### リスク

- OBS の ABI/API 変更追従が恒常コストになる。
- 出力デバイスへの通常出力と OBS タップの二重供給時のクロック差
  （OBS 側はプッシュ型ソースなのでエンジンのクロックで供給すれば良いが、
  underrun 時の挙動設計が必要）。
- コード署名がないと配布時に警告（既存の SmartScreen 課題と同種、`RELEASE_PLAN.md` 参照）。

## 実装フェーズ

| フェーズ | 内容 | 完了条件 |
|---------|------|---------|
| 3-A1 | obws 拡張: ソース自動作成 + 重複ミュート提案 | ワンクリックで OBS に正しいソースが立つ |
| 3-A2 | 接続検証（テストトーン→レベル確認） | 「OBS に音が届いています」を実測で表示 |
| 3-B0 | 技術検証スパイク: 共有メモリ PCM 受け渡しの PoC | OBS でタップ音声が 10 分間途切れず再生 |
| 3-B1 | エンジンタップ + プロトコル本実装 | |
| 3-B2 | プラグイン本体 + 配布パイプライン | インストーラから導入し OBS で動作 |

## テスト

- 段階 A: obs-websocket のモックは困難なため手動中心。`docs/TESTING.md` に
  OBS 28/30/31 での確認手順を追加。
- 段階 B: 共有メモリ層は Rust ユニットテスト可能に分離。長時間連続稼働テスト必須。

## 判断ポイント

- 段階 A 完了後に「それでも仮想ケーブルが障壁か」をユーザーフィードバックで確認してから
  段階 B に着手する。段階 B は本リポジトリとは別クレート/別ディレクトリ
  （例: `obs-plugin/`）として隔離する。
