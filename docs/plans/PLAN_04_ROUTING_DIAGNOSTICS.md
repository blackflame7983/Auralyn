# プラン4: 仮想ルーティングの失敗対策（接続診断）

## 目的

Discord / VB-CABLE / 出力先の「音が届いていない」問題を、名前マッチの推測ではなく
**実測で診断**し、原因と直し方を具体的に提示する。OBS 以外のアプリでも迷わないようにする。

## 現状の確認結果

- `TroubleshootModal` が既に存在するが、チェックは主に静的
  （エンジン起動状態、デバイス名に `cable`/`voicemeeter` を含むか等の名前マッチ）。
- 「Auralyn は動いているのに Discord に音が行かない」ケース
  （Discord 側の入力デバイス誤り、CABLE Output 未選択、Windows 既定デバイスの罠、
  サンプルレート不一致）は検出できない。

## 設計方針: 静的チェック → 実測チェックへの強化

### 診断項目（チェーン順に検証）

| # | 診断 | 実測方法 |
|---|------|---------|
| D1 | マイク入力が生きているか | 入力ピーク（既存メーター）を数秒監視。無音なら「マイクに向かって話してください」→ それでも無音なら OS 権限/ミュート/別アプリ占有を疑う案内 |
| D2 | エンジン出力が出ているか | Post メーターの実測（既存）。テストトーン生成コマンドをエンジンに追加し、マイク無音でも検証可能に |
| D3 | 出力先が仮想ケーブルか物理か | 現在の出力デバイスの分類表示（既存の名前マッチを流用）+「配信/通話用途なのに物理出力」の警告 |
| D4 | 仮想ケーブルの向こう側に音が届いているか | **CABLE Output を一時的に入力として開き、テストトーンのループバック検出**（Auralyn→CABLE Input→CABLE Output を実測。WASAPI で第 2 入力ストリームを短時間開く） |
| D5 | サンプルレート不一致 | CABLE Input/Output の Windows 側共有モードレート取得と、エンジン設定レートの比較。不一致なら「サウンド設定で 48000Hz に統一」を案内 |
| D6 | Discord 等の受け側設定 | プロセス自動検出は不可なため、**チェックリスト形式のガイド**（スクリーンショット付き: Discord の入力デバイスに CABLE Output を選ぶ、ノイズ抑制 Krisp を OFF に、等） |
| D7 | Windows 既定デバイスの罠 | 既定通信デバイスが CABLE になっていて自分の耳に何も聞こえない等のよくある誤設定を検出・説明 |

### 診断フローの UI

- `TroubleshootModal` を「診断ウィザード」形式に改修:
  1. 用途を選択（Discord / OBS / その他アプリ / とりあえず聴きたい）
  2. D1→D7 を自動実行できるものから順に実行、結果を ✅/⚠️/❌ で表示
  3. 失敗項目ごとに「直し方」ボタン → 該当設定モーダルへジャンプ or 手順表示
- 診断結果のコピー機能（サポート/issue 報告用のテキスト出力）。

### バックエンド追加

- `ipc.rs` / `core.rs`:
  - `Command::PlayTestTone { freq_hz, duration_ms, level_db }`（D2/D4 用）
  - `Command::ProbeLoopback { input_device: String, duration_ms }` → トーン検出結果を返す
    （検出は目標周波数近傍の Goertzel 1 本で十分・軽量）
- `devices.rs` / 新規 `src-tauri/src/routing_diag.rs`:
  - Windows のデバイス既定/共有モードフォーマット取得（`windows` crate の
    `IAudioClient::GetMixFormat` 相当。既に依存あり）
- `src/api/audio.ts`: `playTestTone()`, `probeLoopback()`, `getRoutingDiagnostics()`。

## プラン間の連携

- D2/D4 のテストトーン機構はプラン3 段階 A（OBS 到達確認）と共通化する。
- 診断で「ノイズ抑制が強すぎ？」系の相談に踏み込まず、プラン1/2（ボイスチェック）へ誘導する。

## 実装フェーズ

| フェーズ | 内容 | 完了条件 |
|---------|------|---------|
| 4-a | テストトーン生成 + ループバックプローブ（エンジン） | CABLE 経由の到達を自動判定できる |
| 4-b | サンプルレート/既定デバイス検査（routing_diag.rs） | 不一致・誤設定を検出できる |
| 4-c | TroubleshootModal のウィザード化 + 用途別ガイド | Discord 用途で一通り診断→解決導線が動く |
| 4-d | 診断結果コピー機能 | テキスト 1 発コピーで環境情報を共有できる |

## テスト

- Rust: トーン検出（Goertzel）のユニットテスト（合成信号）。
- 手動: VB-CABLE あり/なし、Voicemeeter、レート 44.1k/48k 不一致環境、
  Discord 実機での成功/失敗パターンを `docs/TESTING.md` に追加。

## リスク・注意点

- ループバックプローブ中に第 2 入力ストリームを開くため、ASIO 占有環境では不可
  → WASAPI 共有でのみ実行し、不可時はスキップして手動確認手順を出す。
- テストトーンが配信/通話に乗る事故 → 実行前に「通話中でないこと」を確認するダイアログ、
  音量は −20dBFS 程度に制限。
