# F1b-0 の方式の比較

状態：比較（統括の案）。独立レビューの後に方式を決め、設計を書く。

前提：
- 変わる挙動は `audio-session-f1b0-changes.md` の C1〜C5・N1〜N3（J-17 で承認済み）。
- 今の事実は `audio-session-f1b0-inventory.md`（以下「洗い出し」）。
- 変えないこと：読み取りの境界、旧の通知、既存の文言、受付の記録、`engine_generation`。

## 1. 何を満たせばよいか

| 要件 | 内容 |
|---|---|
| R1（C1） | 停止は、先に並んでいる通常の操作より先に実行する。停止より前に受け付けた開始は実行しない |
| R2（C2） | 書き込みが5秒終わらなければ、その接続を切り離す。書き込みの間、ほかの入口（停止・トレイ・読み取り）が止まらない |
| R3（C3） | 応答の待ちが残っていても、停止を受け付ける。応答のない接続は期限で切り離す |
| R4（C4） | 256件・60秒・90/120秒。停止は断らない・捨てない |
| R5（C5） | 出力だけが閉じた子を、次の操作で切り離して作り直す |
| R6（N1） | トレイ・ショートカットは、呼び出しのスレッド（画面のイベントループ）でロックを待たない |
| R7（N2） | 古い接続の通知を捨てる |
| R8（N3） | 終了の確認でロックを持たない |
| R9 | 85種・95か所の入口と、配信セットの長い手順（洗い出し 1.6）を、互換の試験（K 群）を保ったまま移せる |

## 2. 案

### 案A：actor（設計の 3章・4章のとおり）

1本の actor スレッドが `AudioHost` を持つ。入口は受付（`Admission`）で、受信箱に命令を積む。命令は actor の上で動き、子の応答を待つ間はポンプが受信箱を読み続ける（4.1）。reader・writer・reaper は別のスレッドで、受信箱に入力を積む。

- R1：停止は専用のレーンに積み、actor は通常の命令より先に取り出す。ポンプが待っている間に届いた停止は、段の境目で効かせる。
- R2・R3：writer のスレッドが書き込み、5秒で `WriteDone` が来なければ actor が切り離す。応答の待ちはポンプの期限で解く。
- R6：トレイは受付に積んで、すぐ戻る。
- R9：95か所を `AudioControl::run(|host| …)` に置き換える。同期のメソッドはそのまま actor の上で動く。

**良い点：**
- 最終の形（F1b の `SnapshotCell`、出来事の列、F2 の確認のセッション）と同じ土台になる。

**危険：**
- ポンプが入れ子の待ちの中で受信箱を読むので、再入の順序が複雑になる。PRE-F1b-12 の (2)(3)(8)(9) がすべてここに集まる。
- 1か所で移すと、互換の試験の失敗の原因を特定しにくい。
- 配信セットの長い手順は、actor を長く占有する。

### 案B：順番つきのロックと、作業のスレッド

`Mutex<AudioHost>` は残し、その前に**順番つきの入口**（受付の番号と、停止の優先を持つ待ち行列）を置く。ロックは、この入口が許した順にだけ取れる。子との通信は、ロックの外の writer・reaper のスレッドに移す。

- R1：入口が停止を先に通す。停止より前の開始は、順番が来た時点で受付の番号と `latest_stop_seq` を照合して断る。
- R2：書き込みは writer のスレッドが行い、命令は `WriteDone` を期限つきで待つ。5秒で切り離す。待つ間もロックは持つ。ただし停止は、次の R3 の方法で割り込む。
- R3：停止は「割り込み」の印を立て、今ロックを持っている命令の応答の待ちを、すぐに解く（待ちを `Err(Interrupted)` で返させる）。命令がロックを手放したら、停止が次に入る。
- R6：トレイ・ショートカットは、作業のスレッドに渡して、すぐ戻る。
- R9：入口の置き換えは、`AudioControl::lock` の中だけで済む。95か所の呼び出し元は変えない。

**良い点：**
- 変更が `AudioControl` と通信の部品に集まる。今の同期のメソッドとロックの境界（読み取りの待ち、K 群）がそのまま残る。
- 段階に分けて入れやすい（入口の順番 → writer → reaper → 割り込み）。

**危険：**
- R3 の割り込みは、すべての待ちの箇所（`execute_command` の1か所と、モード VST の経路）で効く必要がある。待ちが1か所に集まっているので実現できる見込み（洗い出し 2.2）。
- 最終の形（actor）に向けて、もう一度移すことになるかもしれない。F1b の `SnapshotCell` は、ロックの外に読み取り専用の値を置けば、案Bのままでも作れる。

### 案C：案Bで入れ、命令を順に actor へ移す

案Bを F1b-0 で入れる。そのあと、F1b・F2 で新しく作る命令（確認のセッションなど）から順に、actor の上に作る。古い入口は案Bのまま残し、移す必要が出たものだけを移す。

## 3. 比較

| 観点 | 案A | 案B | 案C |
|---|---|---|---|
| R1〜R8 を満たすか | 満たす | 満たす（R3 は割り込みで） | 満たす（F1b-0 は案Bと同じ） |
| 互換（K 群・読み取りの境界）を保つ手間 | 大きい（95か所の実行の場所が変わる） | 小さい（実行の場所は変わらない） | 小さい |
| F1b-0 の変更量 | 大 | 中 | 中 |
| 段に分けて入れられるか | 難しい（actor とポンプは一度に要る） | できる | できる |
| 最終の形（F1b・F2・GPUI の分岐）との相性 | よい | ロックの外の値（`SnapshotCell`）で補う | よい（新しいものは actor で作る） |
| 主な危険 | ポンプの再入の順序 | 割り込みの抜け | 2つの方式が並ぶ間の境界 |

## 4. 統括の推奨

**案C（F1b-0 は案B）**を推します。

- C1〜C5 は、利用者から見ると「固まらない・停止が効く・自動で戻る」です。これは、実行の場所を変えなくても、入口の順番と通信の部品で満たせます。
- 今回の手戻りの原因は、一度に動かす範囲の大きさでした（F1a-1 で actor を外したのと同じ理由）。案Bは、互換の試験を保ったまま段に分けて入れられます。
- actor は、F2 の確認のセッションのように、新しく作る命令で使います。ここが一番効くところです。

## 6. 第2版：独立レビューと J-18 を受けた見直し（2026-11-22）

### 6.1 レビューの要点（Sol）

- 案B・案C の「停止の割り込み（`Err(Interrupted)`）」は成り立たない。親の応答の待ちを解いても、子では先の命令が続いている。同じ接続にすぐ `Stop` を送ると、旧の応答を `Stop` の応答として受け取りうる。Start の途中（配信ミックスの準備の後、`Started` の通知の後）で抜けると、子が止まった証拠がないまま `running=false` になる。
- 案Bの R2（書き込みの間もほかが止まらない）と R9（`AudioControl::lock` の中だけで済む）も、書いたままでは成り立たない。
- 案A にも、ポンプに戻らない同期の処理（OS・ファイル・`emit`）と、先に届いた応答を採る記述（設計 4.1。今のコードと PRE-F1b-12 (4) は書き込みの失敗が先）の問題がある。
- 第4の案：**受付・実行の順・状態の持ち主を1つにし、既存の命令はその持ち主への「つなぎ」として段に分けて移す**。停止に関わる経路（Start・Stop・再起動・退役の確認）から明示の段にする。

### 6.2 J-18 で変わること

J-18 で、停止は「実行中の命令の応答を待ってから」になった。したがって、**実行中の命令を途中で打ち切る仕組み（割り込み）は要らない**。停止に要るのは次の3つだけになる。

1. 停止を、並んでいる通常の操作より先に実行する（受付の順番）。
2. 実行中の命令の応答の待ちに、期限がある（書き込み5秒・応答10秒。過ぎたら接続を切り離す。C2・C3）。
3. 停止より前に受け付けた開始を、送る前の境界で断る。

これで、Sol の指摘のうち「割り込みで抜けた命令の後始末」の問題はなくなる。残る問題は、書き込みと応答の契約（6.1 の2点目・3点目）、受付の境界（Start の採番の位置、K11・K12）、読み取りの境界（R2・R8 と K2・K10 の両立）、長い同期の処理の上限。

### 6.3 次に行うこと

1. 方式の候補を **案B'（案B から割り込みを外したもの）** と **第4の案** の2つに絞る。
2. Sol が挙げた2つの場面を、模擬の sidecar で試作して比べる：(a) 子で Start が進んでいる間の停止、(b) 配信ミックスの準備の途中の停止。応答の誤配がないこと、健全な接続を強制終了しないこと、決めた時間の中で停止と後始末が終わることを確かめる。
3. 試作の前に、Neon に方式の筋を見てもらう。
