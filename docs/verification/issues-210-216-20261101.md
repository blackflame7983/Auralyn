# #210〜#216の実機確認（2026-11-01）

発声・物理ループバック配線なしで可能な確認を実施した。
製品コードの基準はmain `44c49b57`、修正後は `a286fca`。検証スクリプトと本記録はその後に追加した。
個人の通常設定は使わず、一時利用領域・専用sidecar・隔離OBSを用いた。
機械可読の集計と実行ファイルのSHA-256は [結果JSON](issues-210-216-20261101.json) に記録する。
元の計測JSON33ファイルはgit外の永続管理領域へそのまま保存し、保存後にも全SHA-256の一致を確認した。
CPUの6試行集計・各60秒以上の完了・比較EXEと測定scriptのhashは独立verifierでも一致した。

- 通常の他アプリは終了させていない。連続運転中は別の開発・検証処理もあり、静穏条件の音声CPU比較ではない。停止中HostのCPU比較中は本作業のビルド・他の実機試験・OBS・開発サーバーを止めた。

## #210 停止中HostのCPU・メモリ

全6試行、18状態の観測が成功した。CPUは各状態3回の平均と、各回平均の最小〜最大を示す。
メモリは3回を通じた同時合計の標本最大、単位はMiBである。

| 版・状態 | CPU平均（各回平均の範囲）% | 最大private | 最大working set |
| --- | ---: | ---: | ---: |
| before・通常表示 | 23.29（23.18〜23.39） | 349.8 | 522.7 |
| after・通常表示 | 2.55（2.22〜2.96） | 341.0 | 535.2 |
| before・最小化 | 21.85（21.54〜22.07） | 361.4 | 553.3 |
| after・最小化 | 0.87（0.78〜0.98） | 350.2 | 557.8 |
| before・トレイ | 25.57（25.20〜25.99） | 337.2 | 538.2 |
| after・トレイ | 0.67（0.50〜0.82） | 314.3 | 525.5 |

afterの最小化はトレイと同じ1%未満の平均へ下がったが、working setの全状態最大は553.3→557.8MiBと微増した。
privateの全状態最大361.4→350.2MiBだけを根拠に、メモリ全体が軽量化したとは結論しない。

測定は隔離した一時利用・音声停止・gamingテーマ・1024×768／DPR 1・設定画面を閉じた状態とした。
device scanを暖機してから、before／after／after／before／before／afterの順に新規Hostを起動する。
各Hostの通常表示→最小化→トレイを各60秒以上、0.1秒間隔を要求して観測する。
初期Issueの通常利用設定とは異なるため、元の45.9%と今回の値を同じ条件として比較しない。
今回のbeforeではトレイでも`document.hidden=false`でpollが続き、元Issueのトレイ2.5%も再現していない。
remote debuggingと観測ラップを残した隔離条件の差を含む比較であり、無観測の通常利用で同じ絶対値になる保証はない。

CPUは1論理core=100%、Hostと観測した子孫の標本の単純平均である。
標本処理時間があるため実際の間隔は0.1秒より長くなる。
端点別のHost／WebView2内訳は両端に存在するprocessのCPU時間差だけで、途中生成・終了した子の負荷は含められない。
新しい子の最初のCPU標本は未初期化として別カウントに残す。
private／working setは同時点のprocess合計の標本最大を使い、各processの生涯最大値を足さない。
標本間の瞬間最大や長時間のメモリ増大を保証するものではない。

計測中はCDPを切断するが、remote debuggingを有効にした起動とtimer／IPC観測ラップは残る。
同じ観測器を両版に用い、source scriptとEXEのhashが全試行で変化していないことを照合する。
状態順は固定であり、経過時間と状態の効果は完全には分離できない。
今回の全差分の比較であって、#210だけの厳密な因果推定ではない。

beforeは通常表示・最小化・トレイのすべてで、`get_engine_runtime_stats`が約1回/秒、`get_audio_state`と`auto_gain`がそれぞれ約1.5回/秒続いた。
afterは通常表示で同程度、最小化・トレイではこれらの観測呼出し数が全3回で0だった。
IPC観測器が有効で、通常表示の実呼出しを捉えていることも照合した。
timerの発火と同期呼出しwall時間はJSONに記録するが、await後・IPC先・描画を含む個別処理のCPU占有率ではない。
IPC／timerの観測窓には前後の暖機・再接続を含む約65秒を使い、CPUの60秒窓とは分けてrate換算している。

追加の原因切り分けとして、beforeの同じ隔離Hostを表示したまま各60秒の段階的な停止を1回行った。

| 操作 | CPU平均（1core=100%） |
| --- | ---: |
| 通常のbefore | 23.72% |
| 全JS intervalを停止 | 20.33% |
| intervalと背景の2つのglow animationを停止 | 0.32% |

この順の差分はtimer停止で約3.39ポイント、追加のglow停止で約20.01ポイントだった。
単一試行・順次操作であり、相互作用と経過時間を分離した関数ごとのCPU帰属ではない。
背景の連続描画がこの条件の大きな要因と分かる一方、特定のhookが厳密に何%かは未測定である。
修正ではgamingの色・形を保ってglowを静止させ、非表示時の状態取得を止めた。

変更前のトレイ移行では既存JSの`window|hide not allowed by ACL`が発生した。
Rust側で実際には非表示になっており、その既知エラーだけをbeforeの測定で許容した。
修正後は重複するJS hide処理を除去し、既存Rustのclose→tray処理へ統一した。
Win32の直接表示だけで行う測定末尾の復帰は、実際のトレイ操作の受入には使わない。
追加診断では、直接表示後にnativeの`get_window_activity=true`でも`appHidden=true`が残り、実native resizeイベントの後には`appHidden=false`へ戻った。
直接表示では通知が来ない場合があることと、nativeイベントから画面更新が復帰することを分けて確認した。
製品の実トレイ経路はRustでshow→unminimize→focus→activity通知を明示しているが、そのクリック自体は自動操作ツールの初期化不良により未確認である。
最小化からの復帰は下記1時間試験で`appHidden=false`とstream継続を確認した。
実際のトレイクリックとホットキーのキー入力による受入は残る。登録保持と模擬IPC試験をキー入力成功へ読み替えない。

## #211 ASIO・VST・録音

### 1時間の連続運転

| 実行対象 | 機器・構成 | 観測時間 | 消費frame増分 | callback増分 | underflow／zero fill／drop／recovery増分 |
| --- | --- | ---: | ---: | ---: | --- |
| main相当の固定dev sidecar | Creative ASIO、96kHz、実384frame、入力5/6→出力1/2、NR high＋内蔵broadcast/0.7＋OTT 3本 | 3600.419秒 | 345,610,752 | 900,028 | すべて0 |
| 修正後の製品release Host、最小化 | Voicemeeter Insert ASIO、96kHz、実512frame、入力7/8→出力1/2、同じ処理構成 | 3600.236秒 | 345,765,888 | 675,324 | すべて0 |

両方とも入力gain=1、出力gain=0・mute=true。チャンネル表記は1始まり、内部指定は0始まり。
各観測窓で入力・要求・消費frameの進行、同じepoch、stream稼働、VST 3本の有効状態を照合した。
製品Hostでは`document.hidden=false`でも`appHidden=true`となり、最小化中の画面更新を抑えたまま音声が稼働した。
通常表示へ戻すと`appHidden=false`、stream running=true／streamFailed=falseだった。

製品Hostの録音は開始付近・中間の加工前後、各5秒・96kHz・480,000frame・2chの計4ファイル。
開始付近はpeak/RMS 0、中間は加工前peak 0.98504／RMS 0.28420、加工後peak 0.39150／RMS 0.08835でfiniteだった。
固定素材ではなく、無発声の仮想入力に含まれた信号の音源は同定していない。音声ファイル自体はリポジトリへ登録しない。
予定した終端の録音は観測窓数の都合で取得されなかった。1時間連続WAVと録音欠損数の確認ではない。
callback間隔の揺らぎを示す`glitchCount`増分はCreative 359,986、Voicemeeter 359,198だった。
既存の判定閾値に対する回数で、これを音切れ回数に置換しない。

### 最新releaseのbuffer要求と固定信号

64／128／256／512frame要求の各ASIO開始に、Creativeの384frame開始を加えた9回が成功した。
Creativeは全要求で実384、Voicemeeterは実512frameだった。各2秒観測の消費frame増分は192,000、zero fill等の増分は0。
対応していない64／128／256frameの物理遅延基準を取得できたとは扱わない。

別途、送信・受信を独立sidecarに分け、WASAPIの仮想CABLEだけへ1kHz・-30dBの試験信号を送った。
送信側input gain=0、受信側output gain=0・mute=trueでフィードバックを防いだ。
48kHz・512frame要求で、実callbackは480〜1056frameだった。
各構成の加工前後は2ch・finite・同じframe数で、約4.4秒の録音だった。

| 受信側処理 | raw peak | 加工前後の差分RMS | 観測区間のzero fill等の増分 |
| --- | ---: | ---: | --- |
| NR OFF・内蔵OFF・VST 0 | 0.00316238 | 0 | 0 |
| NR OFF・内蔵OFF・OTT 3本 | 0.00316238 | 0.0602723 | 0 |
| NR ON・内蔵broadcast/0.7・OTT 3本 | 0.00316238 | 0.0487324 | 0 |

最初の観測前に96frameのzero fillとunderflow 1回が記録されていた。測定区間内で増えていないことと、開始時から0であることを区別する（関連#201）。
この結果は実VST処理・録音経路の確認であり、歌声品質、聴感、物理的往復遅延の基準値ではない。
実OTTのload→editor open→unload試験も別途1件成功した。表示画素やDPIの確認ではない。

物理配線・段別実信号遅延・各条件5回の往復遅延・固定素材の1時間連続録音による欠損解析は未実施。
利用者の配線なし指定を維持し、#211は部分対応として残す。[表示値との関係と今後の手順](../LATENCY_MEASUREMENTS.md) を参照。
