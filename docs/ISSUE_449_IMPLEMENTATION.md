# 無音と処理停止の区別（#449）

メーターが 75 ms データを受け取らないと 0 を送るため、音量が 0 の無音と、コールバックや処理が止まった状態はメーターだけでは区別できない。この変更は検知と通知だけを行い、再起動・ミュート・ミュート解除はしない。

## 判定

制御スレッドが約 250 ms ごとに、合成時刻を注入できる `ProcessingWatch::observe_at` へ次を渡す。

- 進捗は、OS 出力コールバック回数と、処理完了数（既存の `CallbackDiagnostics.count`）のどちらかが進んだこと。
- 停止までの待ちは `max(500 ms, block_period × 8)`。500 ms は、短いバッファの数ブロック分の揺らぎを停止にしない下限。8 ブロックは、1〜2 回の取りこぼしでは出さず、その先が続かないときだけ出すための幅。
- 出力コールバックも処理も止まっていれば `outputCallback`。出力コールバックは来ているのに処理完了が進まなければ `processing`。
- 開始直後は、最初の進捗を見るまでと、起動から 1 秒の両方を過ぎるまで判定しない。デバイスが最初のコールバックを出す前の無音を停止にしないため。開始試行ごとに出力回数と処理完了数は 0 から作り直す。最初の観測がすでに非ゼロなら、その前に進んだ分を最初の進捗とみなす。
- 音量が 0 でも、両方の進捗が途切れていない場合は警告しない。

直近の異常は累積値ではなく、構築時に確保した 512 件のリングへ増分だけを入れる。60 秒から外れた分は数えない。60 秒に underflow が 3 回以上、または遅着が 10 回以上のときだけ「回数が多い」と出す。3 回は、起動後の散発 1 回を通知にしない下限。10 回は、遅着が可聴の音切れではないため、周期へ追いついていない傾向が見えるまで出さない下限。リングを 64 件にすると、250 ms 観測を 60 秒続けると窓の古い増分が落ちる。512 件は遅着と underflow の両方を 60 秒ぶん保持する。

## 除外

次では内部状態を捨て、猶予からやり直す。停止の警告は出さない。

- 開始試行（`queue_attempt`）が変わった。
- `running` が偽になった。稼働中は、出力ストリームがあり、かつキュー状態が `Running` のときだけ。
- いずれかのカウンタが前回より小さい（作り直しや、u64 の巻戻り）。

モード無音で入力を止めている間（`pause_sources`）も判定しない。出力を無音へ寄せているだけで入力コールバックがまだ動く区間は、従来どおり監視する。この間に増えた遅着と underflow は直近回数へ入れない。

underflow は、キューが空で読めなかったコールバック数から、起動時分を引いた値を警告の窓に入れる。プロセス音声が再primingを待っている間の不足は、この警告の窓に入れない。出力コールバックと処理完了の監視はその間も続ける。queue診断の累積 `underflow_callbacks` と `startup_underflow_callbacks` の意味は変えない。

## 監視する主体

| 止まったもの | 誰が気づくか |
| --- | --- |
| RT の出力コールバック、または処理完了 | engine の制御スレッド。`audio-processing-health` と `RuntimeStats.processingHealth` |
| engine の制御スレッド自体、sidecar の終了 | 既存のまま。コマンドの `recv_timeout(10 s)`、統計取得の失敗、stdout の EOF による `audio-error`。今回ここに新しい検知は足していない |
| 統計の取得が、一度成功したあと失敗または 2.5 秒失効した | UI。`useRuntimeStats` が「音声処理の状態を取得できません。」を出す。最初から一度も取れていない間は出さない |
| UI スレッド自体 | アプリの中では自己検知できない |

OS 出力コールバック回数は既存の atomic では取れない。`frames_processed` は処理したフレーム数で、分離時は OS コールバックではなく処理側で増える。そのため出力用と入力用に `AtomicU64` を 1 個ずつ足し、コールバックごとに `fetch_add(1, Relaxed)` だけを行う。プロセス取得の入力は cpal の入力コールバックを通らないため、この入力回数には含まれない。停止判定は出力コールバックと処理完了だけを見る。

## 遅着・underflow と、聞こえた音切れ

遅着（`glitch_count`、画面の累積グリッチ回数）は、出力処理の入口間隔が直前ブロックの周期の 1.5 倍を超えた回数である。underflow は、キューが空でサンプルを読めなかった回数である。どちらも、耳で聞いた音切れの回数ではない。#319 の原因調査とは別であり、この通知を原因の特定として扱わない。

## 自動で再開しない

止まったことを検知しても、エンジンの再起動、ミュート、ミュート解除はしない。誤検知で配信中の音を切らないためである。既存の `useAudioRecovery` の挙動は変えていない。画面は、設定にある「音声処理を再起動」を自分で使う案内だけを出す。統計が届くまでは `audio-processing-health` を表示に使う。`audio-stopped`、`audio-error`、`audio-stream-error`、`audio-started` でその表示を消し、統計が来ないときは 2.5 秒で失効する。稼働中でなければ出さない。

## 実機

処理を故意に止めて、この警告が出ること、および無音だけでは出ないことは、この作業では実機確認していない。単体試験は合成した `Instant` とカウンタであり、WASAPI / ASIO の実コールバック停止や聴感の証拠ではない。
