# 利用者向けドキュメントの運用

利用者向けの説明（使い方・手順・困ったとき・用語）の置き場所と、アプリ・公式サイトとの分担を定める正本。
開発者向けの文書（この `docs/` の他のファイル）とは分ける。

## 1. 目的と分担

ヘルプは最後の手段とし、まず画面そのものが次の1手を示す。説明は次の4層に分け、下の層ほど使う回数が少ない前提で作る。

| 層 | 置き場所 | 中身 |
|---|---|---|
| ① 画面そのもの | アプリ | ラベル・状態・押せない理由で、次の1手が分かる |
| ② その場の説明 | アプリ（情報ボタン） | 1〜2文で意味を伝える。「詳しく」からドキュメントの該当箇所へ移れる |
| ③ 使い方 | アプリ（ヘルプメニュー・F1） | 最低限の要約だけ。オフラインでも読める |
| ④ ドキュメント | 公式サイト `/apps/auralyn/docs/` | 手順・背景・症状別の対処・設定の説明。細かい説明はすべてここに置く |

原則:

- 本番中は読ませない。トラブルでは原因の区分と次の1手だけを示し、説明は本番後に読めればよい。
- 押せない理由は、ヘルプではなく画面に出す。
- 手順（OBS・通話への送り方）と画面の説明を分ける。
- 同じ説明を2か所で管理しない（4章）。

## 2. 原稿の置き場所

- 原稿の正本は、このリポジトリの `user-docs/` に置く。日本語は `user-docs/ja/`、英語は `user-docs/en/`。ファイル名はページ名と同じにする（例 `user-docs/ja/troubleshooting.md`）。
- 公式サイト（`blackflame7983/tech-trend-site`）は原稿を書き換えない。サイト側には表示と同期の仕組みだけを置く。
- サイトへの反映は「同期 PR」で行う。サイト側の手順が、指定したタグの `user-docs/` を取り出してサイトの中へ写し、PR を作る。確認してマージし、サイトの通常の手順で公開する。

## 3. ページと URL の約束

最初の10ページ（URL は `/apps/auralyn/docs/` の下。英語版の URL はサイトの言語の扱いに合わせる）:

| ページ名 | 題 | 答える問い |
|---|---|---|
| `index` | はじめに | 何ができて、何が要るか。全体の流れ |
| `setup` | はじめの設定 | セットアップの各手順の意味と選び方 |
| `obs` | OBS へ送る | 仮想ケーブルの選び方と OBS 側の設定 |
| `discord` | 通話で使う | Discord などの入力の設定 |
| `home` | ホームの見方 | 本番帯・メーター・音調整・音声チェック・右の列 |
| `sound` | 音を整える | ノイズ低減・声を整える・VST・歌と雑談のモード |
| `troubleshooting` | 困ったとき | 症状別（音が出ない・届かない・途切れる・遅れる・VST が読めない） |
| `settings` | 設定の説明 | タブごとの項目と、いつ触るか |
| `shortcuts` | ホットキー | 操作の一覧と割り当ての注意 |
| `glossary` | 用語集 | 言葉の意味 |

約束:

- ページ名と、アプリから飛ぶ見出しの印（アンカー）は、一度公開したら変えない。廃止するときは転送を残す。
- 見出しの印は自動生成に任せず、原稿で明示する（例 `## 音が出ない {#no-sound}`）。日英で同じ印を使う。
- アプリが使うリンクは `user-docs/links.json` に集める（`名前 → ページ名#印`）。アプリは URL を直書きせず、この名前で参照する。
- 試験で両側から確かめる。このリポジトリでは、一覧のページと印が日英の原稿に実在すること。サイトでは、同期した原稿のすべての印がページに出ること。
- アプリから開く URL に、利用者の情報や追跡用の値を付けない。

## 4. 正本とずれの防止

- 原稿の引用括弧（「」・“ ”）はUI名専用とし、front matterの `uiLabels` に列挙した名称と本文中の引用の集合を一致させ、日英それぞれの文言カタログの値と試験で完全一致を照合する。

- 用語の正本は `user-docs/{ja,en}/glossary.md`。各語に短い説明（1文）を持たせ、アプリの「使い方」の「言葉の意味」はそこから作る。アプリ側に別の説明を書かない。
- 原稿で「」（英語は “ ”）で囲んだボタン名・画面の名前は、アプリの文言カタログ（`src/i18n/messages.ts`）に実在する文字列にする。試験で確かめる。
- 表記は `docs/COPY_GUIDELINES.md` に従う。用語の選び方は `docs/DESIGN.md` の用語集と矛盾させない。

## 5. 版の扱い

- サイトには、最新の安定版のタグの原稿を出す。新しい機能の説明には、使える版を書き添える（例「v1.2.0 以降」）。
- 挙動・画面の名前を変える PR では、`user-docs/` と `user-docs/links.json` も同じ PR で直す。
- リリースのとき（`docs/VERSIONING.md` の手順の後）に、そのタグで同期 PR を作る。誤記の急ぎの修正は、同期 PR で取り出すタグや参照を指定して出す。

## 6. アプリ側の最低限

- 「使い方」（③）は、ホームの見方の要約、困ったときの1手、キー操作、短い用語の説明に限る。各節から、対応するドキュメントへ移れるようにする。
- 主な情報ボタン（②）には、対応するドキュメントの印があれば「詳しく」を付ける。
- ネットにつながらないときも、①〜③だけで本番の操作と復帰ができること。

## 7. 合格の条件

1. 10ページがそろい、日英で読める。
2. アプリの主な情報ボタンと「使い方」から、該当箇所へ1回で移れ、リンク切れを試験で防いでいる。
3. 原稿のボタン名と用語がアプリとずれないことを、試験で確かめている。
4. アプリ側の「使い方」が要約だけになり、細かい説明はドキュメントにある。
5. 同期 PR の手順で、指定したタグの原稿をサイトへ反映できる。
