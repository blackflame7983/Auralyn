# Auralyn 機能監査と最適化

2026年10月31日。対象は `c18f2b0` を起点とするローカルコード。

入力チャンネル監視の信号取りこぼしと、サンプルレートの表示不一致を修正した。
次に優先するのは、入力より出力のチャンネル数が少ない場合の入力選択、接続先の下書きと稼働値の混在、ボイスチェック解析の音割れ見落としである。
処理負荷の改善候補は見つかったが、CPU使用率や音切れの改善率は未計測である。

## 対象と方法

機器列挙、ASIOの入力選択、サンプルレートとバッファの選択、内蔵処理、歌向け帯域調整、録音解析、メーター、状態取得、主要な大規模ファイルを調べた。
設定画面からAPI、Host、エンジンへの呼出しを追い、保存値と稼働値、非同期処理、音声コールバック内の処理を照合した。
OBSとVSTは、主に設定・制御・分割境界を確認した。全プラグインや全機能の実機受入を行ったものではない。

実行環境の通常設定、音声デバイス、OBS設定は変更していない。
実際のASIO入力、聴感、OBSへの到達、長時間負荷、DPI・読み上げの確認は別途必要である。

## 今回修正した問題

### 通知間の入力ピークを保持する

旧 `audio_engine/core.rs` は、チャンネルピーク配列をコールバックごとに初期化し、固定4800フレームの通知条件に当たったブロックだけを送っていた。
通知対象外のブロックに入った短い音は、入力選択画面の「信号あり」に反映されなかった。
固定4800フレームでは、48kHz以外で通知頻度も変わる。

状態を `audio_engine/channel_scan.rs` に分離し、実レートから求める約100msの区間内でピークを保持する。
キューが満杯なら送信成功まで保持し、制御側で複数の通知を排出するときもチャンネルごとの最大値を統合する。
監視の切替とストリーム再生成には内部世代を付け、前の監視結果を採用しない。
世代が変わった後の最初のゼロ通知は省略しない。

外部イベントの32要素配列、入力ゲイン適用後の検出、入力の経路は維持した。
音声側は固定配列と非ブロッキングのキューを使い、確保・解放を伴わない経路を試験する。
制御側の配列からVecへの変換は、キューから取り出すたびに行う処理から、イベント送信時の1回に減らした。

### 代表値以外のサンプルレートも現在値として表示する

`AudioSettingsModal.tsx` の詳細設定は、44.1/48/96kHzの3候補だけだった。
88.2/192kHzなどが稼働値として渡されると、Reactの保持値に対応する選択肢がなく、画面の表示と開始要求値が一致しなかった。
現在の選択値を候補へ追加し、88.2/192kHzの表示と開始引数を回帰試験で確認した。

これは現在値の表示を守る修正であり、各機器が対応するレートの一覧取得を追加するものではない。

## 未修正の不具合を先に解消する

### 入力より出力のチャンネル数が少ないと選択した入力を使えない

`audio_engine/core.rs` は `current_channels` に出力のチャンネル数を保持する。
入力コールバックの `queue_diagnostics::push_mapped_frames` も、入力を出力のチャンネル数に合わせてキューへ入れるため、それを超える入力チャンネルはこの時点で失われる。
その後の `SetInputChannels` は出力数に基づいて選択を正規化する。

たとえば入力8ch・出力2chで入力3/4を選ぶと、画面では入力能力に基づいて選択できても、エンジンは範囲外として1/2へ戻す。
APIは正規化後のペアを返さず成功を返すため、画面と保存値は3/4のままになり得る。
監視も出力数に変換した後なので、今回修正したピーク保持だけでは高位入力の検出を回復できない。

優先度は高い。入力の収集・監視と、内部ステレオ処理、出力への展開を分ける必要がある。
入力ペアを出力数へ変換する前に適用し、正規化後の実値を画面へ返す設計を先に定める。
入力8/出力2、入力2/出力8、モノラル、選択先だけに信号がある条件で、監視・録音・VST・実出力が一致する試験を追加する。

### 接続先の下書きと現在の入力操作が混ざる

11月1日のPR前レビューで、入力ペアの通知が未適用の接続設定まで親へ保存する経路を修正した。
通知は適用済みhostとinputChannelsだけとし、IDなしASIO設定でも未適用の機器へ保存・再起動できる回帰試験を追加した。
以下は監査時の原因説明である。監視表示と実際の稼働機器の結び付け、接続先変更中の入力ペア操作を下書きとして扱う設計は引き続き残件である。

根拠は `src/components/features/AudioSettings/AudioSettingsModal.tsx` の `InputChannelSelector` への `onChannelMapped` と、`src/hooks/useAudioConfig.ts` の `handleConfigUpdate`。
入力ペアの操作は現在動作中のエンジンへ即時送信される。一方、その成功通知は編集中のホスト・入出力名・レート・バッファをまとめて親へ渡し、保存する。

たとえば機器Aで稼働中に、保存して開始を押さずに機器Bへ選択を変え、入力ペアを操作すると、機器Aへチャンネル変更を送りながら保存名は機器Bになる。
機器IDはこの通知に含まれず、親が既存IDを引き継ぐため、名前とIDも食い違い得る。
同じチャンネル数の機器への切替では監視表示の初期化も起きない。`InputChannelSelector.tsx` が初期化の依存に使うのは `maxChannels` だけである。

優先度は高い。稼働中の機器IDと編集中の機器IDを分け、監視と即時変更は稼働中の機器にだけ結び付ける。
接続先を編集中ならペアも下書きとして扱い、開始成功後にまとめて保存する方式が候補となる。
同名機器、開始失敗、停止中、移行確認中の挙動まで揃える設計変更は、今回の通知修正とは分けて残している。

### 左右平均によって音割れを見落とす

`src-tauri/src/audio_analysis.rs` の `analyze_voice_check` は、`to_mono` で左右を平均してから `detect_clips`、音量、音切れ、帯域を解析する。
左右が `[1.1, -1.1]` なら平均は0になるため、各チャンネルがしきい値を超えていても音割れ判定へ届かない。
片側だけの大きな信号も平均で小さくなる。

音割れは左右それぞれの絶対値で判定し、音量・帯域は左右のエネルギーを集計する方向で修正する。
平均によるモノラル互換性の確認が必要なら別の項目として維持する。
解析結果と助言の意味が変わるので、逆相、片側入力、ステレオ残響を含む回帰試験と合わせて進める。

## 負荷削減は表示と解析から進める

| 候補 | コード上の根拠と影響 | 次の実装と確認 |
| --- | --- | --- |
| 無音時のメーター再描画を止める | `useMeterLevels.ts` は16msごとに新しいstateを生成する。`MeterContext.tsx` は入出力で各1本使い、silent状態でも更新が続く | 値が変わった場合だけ公開し、微小な差は0へ収束させる。ピーク保持、クリップの経過秒数、停止・再開・staleの更新は維持する。無音・有音・非表示で描画回数を比較する |
| 状態取得を共有する | `MasterBar.tsx` は1秒、`VoiceQuickControls.tsx` は2秒で同じ `getEngineRuntimeStats` を要求する。設定も別に取得する | 1つの購読元とイベント後の再取得に寄せる。古い応答の排除、取得失敗時の警告、非表示時の扱いを各利用者で維持する |
| 監視を必要な間だけ動かす | `Engine::new` の `scan_enabled` はtrue。入力選択を一度も開いていなくても開始後に監視する | 通常開始時は無効、選択画面の使用中だけ有効にする候補。複数利用者や開閉中の遅い応答を扱う所有権を先に定める |
| 録音解析のFFT計画を共有する | `audio_analysis.rs` の `octave_band_deltas` は同じ長さのrawとprocessedに対し、`magnitude_spectrum` 内でそれぞれ計画を作る | 1回の解析内で計画を共有する。まず出力同値と解析時間・最大メモリを測る。区間解析への変更は指標の変更として別に扱う |

これらの負荷削減率は未計測である。通知間隔を延ばすだけでは復旧検知が遅れるため、共通化と変更検知を先に検討する。
音声側で全チャンネルを展開している処理も候補になるが、複数チャンネルを扱うVSTや入出力形状に影響する。ステレオ2chだけに省略する変更は現段階では採用しない。

## 周波数の選択は用途ごとに扱う

サンプルレートは `core/capabilities.rs` が起動試行ごとの能力を保持し、ASIOでは入出力の共通レート・F32・既定チャンネル構成を確認する。
この仕組みは維持する。設定画面の候補は機器の対応一覧ではないため、将来は選択機器の能力と実際の稼働値を分けて表示する。
一覧表示のために全ASIOドライバーを開く方式は、現行の選択機器だけを開く方針と相反するため採用しない。

音質調整では `singing.rs` の低域カット40〜160Hz、明るさ±3dBと、`SingingControls.tsx` の入力範囲が一致している。
明るさは3kHz付近を基準とする棚型フィルターで、任意の帯域を選ぶEQではない。
`singing_proposal.rs` の自動候補が40/60/80/100Hzに限定される点は、手動の上限160Hzと異なるが、それだけでは不具合としない。
自動候補を広げる場合は、声の低域を削り過ぎない判定と聞き比べを先に用意する。

## 分割は変更理由が異なる責務から進める

`audio_engine/core.rs` の `start_audio_attempt` は、機器選択からストリーム生成、コールバック、失敗時の再試行まで約2000行にまたがる。
`handle_command` も多数の機能の状態変更を持つ。
先に「起動計画の作成」「確保済みコールバック状態」「ストリーム構築と回収」を分けると、失敗時にどの資源を回収するかを確認しやすくなる。
音声処理順序や非同期処理の境界を変える一括分割は避け、今回のチャンネル監視のように独立した状態と試験を持てる単位から進める。

次は `AudioSettingsModal.tsx` の接続設定と適用処理を独立させる。
上記の下書きと稼働値の混在を解消する境界として使い、見た目だけのタブ分割で済ませない。
保存と再起動で共通する機器ID・実レート・チャンネル・保存の手順を整理し、移行確認とVST復元の違いは維持する。

`audio.rs`、`commands/bundles.rs`、`vst_host/instance.rs` などの大きさには同居する試験コードも含まれる。
試験を隣接モジュールへ移す整理と、本体の責務分離は別に評価する。
翻訳辞書 `messages.ts` は大きいが、行数だけを理由に実行時の読み込みや型の契約を変える優先度は低い。

## 改善順序と検証

1. 入力と出力のチャンネル数が異なる場合の経路、接続下書きと稼働値の分離、左右別の音割れ判定を修正する。
2. メーターの変更時更新と状態取得の共有を実装し、描画回数・IPC回数・CPUを測る。
3. 起動処理と設定適用を段階的に分割する。
4. 実ASIOの短い入力、32chを超える機器、各レート・バッファ、実VSTとOBSへの到達を受け入れる。

入力候補が32chを超えて表示されても、監視イベントは現状32chまでである。
33ch以降を「無信号」と断定しない表示と、必要に応じた監視範囲の拡張は未実装である。

原因をコードの不具合と確定せず、同時負荷がある条件での失敗記録として残す。

実装と試験はTerra担当へ限定委譲し、監査の統合と最終検証は親が実施した。

コミット、push、PR作成、sidecarの通常アプリへのコピー、公開は行っていない。
