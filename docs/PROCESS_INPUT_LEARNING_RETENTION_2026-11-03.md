# 停止・入力切替で学習値を失う不具合を修正した

2026-11-02〜03、実素材のプロセス入力と、機器入力への復帰を実Engineで確認した。
声の用途でNRのOFF→ON→OFFは動作したが、停止後に元の入力へ戻ると学習値が初期化される不具合を発見し、修正した。
NRの方式・強度の既定値は変更していない。

## 学習値の所有元を停止中も保持する

従来の`clear_audio_resources`は、学習値を保持したまま`noise_input_identity`だけを消していた。
次の開始時には、その値をどの入力用に退避するか分からず、新しい学習状態へ置き換えていた。
直接`bind_noise_input`を往復する既存テストでは、実際の停止処理を通らないため検出できなかった。

[停止時の回収処理](../src-tauri/src/audio_engine/core.rs)で学習値と入力の対応を残し、次の入力を束縛するときに既存の退避・復帰を行うよう修正した。
測定の有効性は停止時に失効させる。値を保持することと、その値を現在の環境で確認済みと表示することは分ける。
追加した[回帰テスト](../src-tauri/src/audio_engine/core/input.rs)は同じ入力への再開、別入力との往復、開始失敗と共通の回収処理の繰り返しを扱う。
回収は制御側で行い、音声callbackへ確保・待機・I/Oを追加していない。

## 実Engineで実素材のNR切替と学習値の復帰を確認した

[明示検証runner](../scripts/verify_process_material_nr.py)は通常の設定から分離したEngineを起動する。
利用者提供素材の1区間を専用Chromeで再生し、別の原音用出力をミュートして取得した。
返しもEngineの最終出力でミュートし、ボイスチェックの加工前後を保存した。実行中の聴感確認は行っていない。

- 声の用途でNRをOFF→ON→OFFとし、それぞれ4秒・48 kHz・ステレオの加工前後を録音した。
- NRがOFFの2回は、各録音の加工前と加工後がサンプル単位で一致した。ONでは同じ録音内の加工前後に差があり、実際のNR有効状態も一致した。
- プロセス開始応答の機器入力IDは空で、取得は失敗していない。各録音は異なる再生時点のため、3回の音質比較や声の保持の判定には使わない。
- 音楽の用途ではNR設定をONにしてもNRが適用されず、声向け学習を拒否することを確認した。

学習の分離は、CABLE Outputを機器入力の代表として使い、所有する制御音だけを測定・承認した。
人の声を含む配信素材は、話さずに測ったノイズとして承認していない。

| 状態 | 測定RMS | 適用済み混合量 | 現在の条件で利用可能 |
| --- | --- | --- | --- |
| 機器入力で制御音を測定・承認 | 0.001414 | 0.55 | はい |
| 配信素材のプロセス入力から機器へ戻る | 0.001414 | 0.55 | いいえ |
| プロセス入力の開始失敗後、機器へ戻る | 0.001414 | 0.55 | いいえ |
| プロセス側で別の制御音を測定・承認 | 0.008485 | 0.68 | はい |
| 再び機器へ戻る | 0.001414 | 0.55 | いいえ |
| 再び同じアプリのプロセス入力へ戻る | 0.008485 | 0.68 | いいえ |

修正前の実行では、最初の機器復帰でRMSが0・混合量が0.6へ戻り、検証が失敗した。
修正後は上表を確認でき、全再生先のミュート・音量・既定ロールも実行前と一致した。
この試験は実WASAPI機器入力とプロセス入力の所有関係を確認するもので、物理マイクやASIOドライバーによる測定は代用しない。
保持は同じEngine内の入力切替に対するもので、Engine終了後の永続保存を追加したものではない。

## Chromeの音声子プロセス終了後は、Chrome側の読み直しが必要だった

[異常時runner](../scripts/verify_process_input_faults.py)の`--audio-service-restart`で、所有するChromeの音声serviceだけを強制終了した。
ルートのPID・生成時刻と子孫関係を確認し、通常のChromeや他の作業のプロセスは対象にしていない。

最初の判定は子プロセスの再生成と古い取得カウンターを使っており、不十分だった。
終了直前を基準に、新たな非ゼロ音声・音声待機の解除・入力ピークも必要とする条件へ直して取り直した。
その結果、Chromeのaudio要素が一時停止し、play操作だけでは再生位置が進まないことを確認した。

専用Chrome側で素材を読み直すと、同じルートの対象のまま、Auralynで再選択せずに取得が戻った。
今回の観測では終了から約7.48秒、終了直前から新たに59,360非ゼロフレームを取得し、待機状態も解除された。
この時間はChrome側の再開操作を含む1回の観測で、Auralynだけで自動復旧する保証ではない。
試験用の読み直し操作を、製品が他アプリへ自動送信する機能は追加していない。

同じ新版で、ルート終了後の停止、古い対象の拒否、明示再選択、別出力への変更・原音ミュート解除時の停止も確認した。
全再生先の設定を保持した。機器の物理切断・無効化、Windows既定出力への移動、通常のChromeプロファイルなどは残る。
