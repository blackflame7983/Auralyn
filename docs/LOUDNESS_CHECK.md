# 出力の音量チェック（Issue #4・改修計画3）

既存のエフェクト一覧の上で、必要なときだけ音量を測定する。
最終出力ゲイン・ミュート・出力チャンネル選択を反映し、デバイスに渡す実サンプルを測る。
ゲーム音を含む配信全体の判定と声の検出は行わない。
測定だけでは音量を変更しない。別操作の「音量を合わせる」での固定ゲイン提案・調整前後の比較は [AUTO_GAIN.md](AUTO_GAIN.md) を参照する。
テスト音とボイスチェックの試聴も、出力中は測定に含まれる。

## 計測と判定

- K-weighting後のステレオエネルギーを100msずつ集計し、直近3秒の短時間LUFSを計算する。積分ラウドネスではない。
- 同じ物理出力チャンネルを左右に選んだ場合は二重加算しない。
- 3秒の窓が揃い、約−60 LUFSを超える区間が窓内に1秒以上あり、直近400msが無音相当でないときだけ判定する。声と背景音を識別するVADではない。
- true peakは4相・12タップの補間とサンプルピークの最大値から推定する。直近3秒のピークを表示する。
- 対応範囲は44.1〜192kHz。未知のレートは判定しない。認証済みメーター・全信号での精度保証ではない。
- 初期目標は声用の仮の値として−20 LUFS、幅は±3 LU。−26／−23／−20／−17／−14から選択可能。サービス公式基準や配信全体の推奨値として扱わない。
- 境界に1 LUのヒステリシスと800msの継続条件を設ける。−1 dBTPを超えるピークはLUFSの準備状態にかかわらず、次の測定イベント（約100ms周期）で「大きすぎ」とする。短い音の後の無音でも、直近3秒に過大ピークが残る間は警告する。
- 測定を停止、音声を停止・再起動、ストリームエラーが発生した場合は表示を消す。測定IDで遅延イベントを除外し、1.5秒以上データが途絶えた場合も過去の判定を消す。
- 目標の変更は当該画面セッション内だけで保持する。音声ゲインやOBS設定は変更しない。
- 開始・停止の応答が失われた場合は停止済みと断定せず、「測定の停止を確認できません」と停止再試行を表示する。入力ストリームエラーは出力停止を保証しないため、測定中のエラーでも停止応答を確認し、失敗時は同じ再試行を表示する。状態未確認中は過去の成功判定を表示しない。ライフサイクルの停止要求と新規開始を直列化し、要求世代で古い完了・失敗を除外する。

## 実装上の制約

音声コールバックでは初期化済みの固定配列と固定容量キューのみを使う。
JSON生成・イベント送信・判定文言はコールバックの外で処理する。
測定停止時はK-weighting・補間・音声サンプルの追加走査を実行しない。
起動時に確保する測定器とキューの小さな固定容量は保持する。
フィルターの両状態がともに1e-30未満になった場合はゼロに戻し、音の後の無音で極小値の計算負荷が続くことを防ぐ。この処理は測定器の内部状態だけに適用する。

## デバイス切替と負荷の診断

ASIO以外へ切り替えるとチャンネル選択を0/1へ戻す。設定保存・エンジン再起動・保存設定からの起動と、エンジン側の両方で適用する。ASIOでは範囲内の選択を維持する。

`get_engine_runtime_stats`の`callbackDiagnostics`は、実際のコールバック回数、最小／最大フレーム数、処理時間の合計／最大値を返す。ストリーム開始ごとにリセットする。CPU比較では同じデバイス・信号・VST状態でウォームアップ後の差分を使う。
`glitchCount`はコールバックの到着が直前の実フレーム数に相当する時間の1.5倍を超えた回数と、固定処理容量を超えるブロックが来た回数の合計で、音切れの実測数ではない。初回の起動待ちは除外する。要求バッファサイズは共有モードなどで実際と異なるため、この判定の基準に使わない。

K-weightingとtrue peakの数式・係数は
[ITU-R BS.1770-5 Annex 1/2](https://www.itu.int/rec/R-REC-BS.1770-5-202311-I/en)、
レート別のK-weighting係数生成は
[libebur128の実装](https://github.com/jiixyj/libebur128/blob/master/ebur128/ebur128.c)
を参照する。公的な適合試験素材一式での認証は実施していない。

## 検証

Rustテストで44.1／48／96／192kHzの1kHz基準波、6dBのゲイン差、無音・不足・リセット・不正値、サンプル間ピーク、処理とresetの無割当／無解放を検査する。
80／800／6000Hzの合成ステレオ波では、FFmpegの`ebur128=peak=true`で得た短時間−20.3 LUFS・ピーク−15.1dBFSとの許容誤差を検査する。
UIテストはIPCとイベントをモックし、未測定・境界・測定ID・再起動・データ途絶・通信失敗を検査する。短い過大ピーク、停止失敗からの再試行、停止待機中の再起動と新しい測定開始も含む。
実マイクの発話、各ドライバー・バッファでの音切れ、CPU負荷・長時間運転、OBS側との音量差は別途確認する。

### 2026-10-17のローカル確認

Windowsのdebugビルドで、合成日本語音声をCABLE Inputへ再生し、WASAPIのCABLE Output（48kHz）から取り込んだ。出力先は別の仮想スピーカーとし、帰還を避けた。900×600で判定・測定停止・出力ゲイン・ミュート・設定保存・エンジン再起動を操作した。
ASIO 6/7からWASAPIへの保存・再起動の両方で0/1へ戻り、手動補正なしで入力・出力レベルが反応した。50%ゲインで出力ピークは半分、ミュートではゼロとなった。音声停止・デバイス変更で測定表示が消えることも確認した。

WASAPIの実コールバックは要求512に対して480〜1056フレームだった。同じ無音ストリーム・VST2個・各約11秒の短時間比較では、測定オフが1コア換算約3.7〜4.3%、オンが約9.0〜10.5%。16論理CPU全体に換算すると約0.23〜0.66%となる。後半には測定オフでも到着間隔のカウンターが増加した。
ASIO（96kHz・512、22ch）ではオフ約38%、オン約49%、VSTバイパスでもオフ約34%だった。ドライバー・入力処理を含む残る負荷や到着間隔の変動は、出力測定器だけに起因するとは判断できない。

測定器を単独で最適化コンパイルした比較では、インパルス後の無音5秒分の処理が修正前約21ms、修正後約10msだった。アプリ全体の改善率ではない。後続のrelease比較は以下のとおり。実マイク、出力の録音・聴取による音切れ判定、長時間・別ベンダーの実機ASIOは引き続き未確認。

### 後続のASIO release比較（2026-10-18文書反映）

Windows 11 Pro build26300、Ryzen 7 7800X3D（16論理CPU）、Rust 1.92、CPAL 0.17.3／asio-sys 0.2.6で比較した。
`cargo build --locked --release --bin audio_engine --bin asio_diag`で最新エンジンをビルドし、UIを除いて直接IPCで操作した。releaseはopt-level 3／LTO／panic=abort。
同じVoicemeeter Insert Virtual ASIO、96kHz、512フレーム、22ch、選択6/7、VST2個の同じ保存状態、ノイズ除去・内蔵エフェクト無効、入出力ゲイン0の無音条件を使った。
起動後10秒、各切替後3秒待機し、各15秒を基本にOFF→ON→OFFを計測した。これは今回のP2修正前の同一Rust測定器での記録であり、UIの修正によるCPU改善を示す比較ではない。

| 音量測定 | debugのCPU（1コア換算） | releaseのCPU（1コア換算） |
| -------- | ----------------------: | ------------------------: |
| OFF      |             34.2〜36.1% |               3.69〜4.19% |
| ON       |                   47.0% |                     3.30% |

CPUはエンジンプロセスの累積CPU時間差分。全16論理CPU換算では各値の1/16となる。UIホスト、Voicemeeter等の別プロセスやシステム全体のDPC負荷を含まない。
短区間の総CPU値は揺れるため、ONの方が軽いとは解釈しない。releaseの平均出力処理はOFF約110〜112µs、ON約140µs、比較中の最大497µsだった。512/96kHzの約5333µsより短くても到着間隔のカウンターは増加した。

入力は参照のみ・出力は無音とする、製品のDSP・VST・入力キューを除いた最小CPALプローブでも確認した。入力のみ／出力のみ／同時、2ch／22chで共通して間隔が偏った。
22ch出力のみでは12秒で2250コールバック・1,152,000フレームを処理し、1180回が約8msの閾値を超えた。20秒再試験も3750回・1,920,000フレーム、閾値超過1975回だった。多くは約4ms未満と約8〜13.3msに分かれ、フレーム総量は96kHz相当だった。これも音切れがない証明ではなく、全増分を誤検知と断定するものではない。
Voicemeeter Virtual ASIO（8ch）でも同傾向だったが、同じベンダーの別インターフェースであり、独立したハードウェアASIO実装の比較ではない。48kHzのASIO試験はクロック設定を拒否されたため未実施。設定を強制変更せず、試験後の既定値96kHz・512と保存設定が試験前と一致することを確認した。

入力キューのサンプル単位転送を抜き出した単独モデルでは、3.003秒分の入力を5試行した中央値が、2chでopt-level 0：約30.5ms／3：約1.78ms、22chで約262ms／約16.0msとなった。ウォームアップで全サンプル一致を確認し、消費側のバルク読み出しは時間に含めていない。
多チャンネルと最適化の影響を裏付ける補足であり、実エンジンの入力CPUを直接プロファイルした結果ではない。opt-level 0にもrelease依存とLTOを使い、Cargoのdebugビルド全体を再現していない。これを実エンジンのCPU内訳へ足し合わせたり、配布アプリ全体の改善率としたりしない。

残る未確認事項は、CPAL・ASIOドライバー・OSのどこで間隔が偏るか、実録音・聴取による音切れ、別ベンダーの実機ASIO、システムDPC、release UIを含むCPU、長時間・実発話・高負荷DSP信号である。プローブと原データはローカルの調査成果物に保存し、製品の処理やドライバーを最適化・置換する変更は含めていない。

### P2修正後の再確認（2026-10-18）

最新のdebugエンジン・ホストを再ビルドし、WASAPIのCABLE Outputから合成音声を取り込み、別の仮想スピーカーへ出力した。900×600で次を確認した。

- 0.6秒へ切り出して増幅した合成音声で、LUFSが準備未完了のまま「大きすぎ」を表示した。true peak推定の最大は約+2.53 dBTP。これは意図的な過大音の検査であり、精度認証ではない。
- 通常の合成音声で「ちょうどいい」、ゲイン50%で「小さめ」、目標を−26 LUFSへ変えると新しい目標に応じた判定を確認した。ミュート中は入力が反応していても出力ゼロとなった。
- WebViewのIPC送信境界で停止だけを一度失敗させた。ネイティブの測定イベントが継続している間も停止未確認・停止再試行を表示し、古い成功判定を表示しなかった。再試行は新しい開始IDではなく停止要求を送り、成功後は停止済みとなり、500ms後以降の測定イベントはなかった。
- 別の停止応答を15秒遅らせ、その間に実際に音声デバイス設定を再適用した。音声停止・開始イベントの後に古い失敗応答が届いても、測定やエラー表示が復活しなかった。注入した送信関数は試験後に復元した。
- 通常の操作、短い過大音、停止未確認、目標詳細の各画面を900×600で確認した。ストリームエラーイベントはなかった。試験後はASIO・96kHz・512・6/7、ゲイン100%、ミュート・バイパス無効、元のVST2個・保存状態へ戻した。

この再確認は前述のASIO性能比較や実出力録音の代わりではない。通信失敗は実アプリへの非破壊的な注入であり、ドライバーの実切断ではない。

### 入力ストリームエラー後の停止確認（2026-10-18追加確認）

入力エラー後に測定停止が失敗する経路も、停止未確認・停止再試行へ統一した。停止応答の成功前には停止済みとせず、古い測定値を受け入れない。音声の再起動が先に完了した場合は古い停止失敗を採用しない。UIテストで失敗・再試行、応答待機、再起動との競合を検査した。

900×600のdebug実アプリで、WASAPI・48kHzの仮想ケーブルへ合成音声を再生し、通常の「ちょうどいい」を確認した。入力エラー通知と停止IPC失敗を注入し、ネイティブ測定イベントが継続していても停止未確認・再試行ボタンが表示されること、再試行成功後は500ms以降の測定イベントがないことを確認した。
別の入力エラー通知では停止応答を15秒遅らせ、既存の自動復帰処理による実エンジン再起動が約2.3秒後に完了した後で停止失敗が届いても、古い測定やエラー表示が復活しなかった。
通知とIPC失敗はいずれも非破壊的な注入であり、ドライバーの実切断試験ではない。試験後は元のASIO・96kHz・512・6/7へ戻し、保存設定全体と音声設定ファイルの試験前後の一致、注入した送信関数の復元を確認してアプリを終了した。
