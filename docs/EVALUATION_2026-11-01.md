# アプリ評価の結果（2026-11-01）

[アプリ評価の軸と測定方法](EVALUATION_CRITERIA.md)に沿った初回の評価記録。

## 対象と範囲

- 対象：`main` の `a7eecca`（PR #208マージ後）。評価軸の文書を追加した `c681550` も製品コードは同じ。
- 環境：AMD Ryzen 7 7800X3D（16論理コア）、メモリ31GB、Windows 11 Pro 10.0.26300、Rust 1.99.1、Node.js 22.22.0。
- 実施したこと：自動テスト・静的解析・依存監査の実行、コードと設定の確認、既存の検証記録（`docs/verification/*-20261101.json`）の読み取り、リリースビルドを起動してのアプリ全体のリソース計測。
- 実施していないこと：実マイクでの聴感、往復遅延の実測、長時間運転、競合製品の実機測定、利用者による作業テスト、公開済みインストーラーの取得と確認。

目標案は合意前のため、本書では合否を「目標案に対して」の暫定判定として書く。競合はいずれも実機で動かしていないため、比較は資料比較に限る。

## B. リソース使用量

### 計測の条件

- 現在のコミットから `npm run tauri build -- --no-bundle` で作ったリリースビルド（未署名）を、利用者の通常設定のまま起動した。
- 音声は開始していない（音声エンジンのCPUが0.1〜0.2%で、ストリームは動いていない）。
- `scripts/measure-release-trial.ps1` で、Hostと子孫プロセス（WebView2を含む計8プロセス）を2秒間隔・60秒ずつ計測した。
- CPUは1論理コアを100%とする値。メモリは各プロセスの最大値の合計で、working setは共有ページを重複して数える。
- 各状態1回の計測で、ばらつきの評価には足りない。

### 音声を動かしている状態（参考：開発ビルドの記録）

音声を開始した状態はリリースビルドで測っていない。11/1の開発ビルドの記録（`native-functional-20261101.json` の `app_performance`）では、アプリ全体のCPUは次のとおり。開発ビルドは最適化されていないため、リリースビルドより高く出る。

| 状態（開発ビルド） | CPU（1コア=100%） | private bytes |
| --- | --- | --- |
| 停止中のホーム | 56.9% | 369 MiB |
| 音声稼働中のホーム（無音） | 85.7% | 366 MiB |
| 30秒録音中 | 103.1% | 425 MiB |
| 30秒の解析中 | 153.0% | 603 MiB |

音声エンジン単体（ASIO 96kHz・22ch・ミュート・VSTなし、リリースビルド）は、`post-audit-quality-20261101.json` で約32%（1コア）、private bytes約16MiBだった。22chの全チャンネル監視を含む値で、一般的なステレオ構成より重い条件である。

### 評価

- 停止中でも約0.46コアを使うのは、常駐させて使う配信ツールとしては重い。16コアのCPUでは全体の約3%だが、ゲーム配信のようにCPUを取り合う場面では効いてくる。
- 最小化中も負荷が変わらないのは、利用者の期待と合わない。最小化やウィンドウが隠れているときに、メーターの描画と状態取得を止めるか減らすべきである。トレイ格納中の値から、改善の余地は大きい。#185（無音や非表示時のメーター状態公開を減らす）、#186（状態の重複取得の共有）、#187（チャンネル監視を必要な画面だけで有効にする）と方向が一致する。
- 比較先（Voicemeeter、NVIDIA Broadcastなど）は同じ条件で測っていない。

改善候補（合否には影響させない）：

- **CSPが無効**：`tauri.conf.json` の `security.csp` が `null` で、`withGlobalTauri` が有効。外部コンテンツを読み込まないため現状のリスクは低いが、万一スクリプトが注入されると全コマンドを呼べる。
- **OBSのパスワードを平文で保存**：WebSocketのパスワードを `localStorage` にそのまま保存している（`src/components/features/AudioSettings/ObsConnectionSettings.tsx`）。Windowsの資格情報マネージャーなどへの移行を検討する。
